# 조사 작업 인계

사전 조사와 ASOS 분석을 합치는 작업을 중간까지 하고 멈췄다. 이 문서는 어디까지 됐고 무엇이 남았는지, 이어서 하려면 무엇을 읽고 무엇을 하면 되는지를 적는다.

- 멈춘 날: 2026-10-07
- 멈춘 이유: 작업에 쓰는 AI 사용량 한도
- 인계한 사람: 박상명

## 어디까지 됐나

| 단계 | 내용 | 상태 | 결과가 있는 곳 |
| --- | --- | --- | --- |
| 사전 조사 | 웹 조사 9건과 출처 검증, 데이터 분석 3건과 재현 검토 | 끝남 | [`prestudy/`](prestudy/)의 `research_*.md`, `data_*.md` |
| ASOS 분석 | 기상청 관측 자료로 한 분석 4건과 재현 검토, 업로드 파일 | 끝남 | [`asos-report.md`](asos-report.md), [`../../datasets/`](../../datasets/) |
| 보완 조사 | 빈 곳 6건을 다시 조사하고 검증 | 끝남 | [`prestudy/`](prestudy/)의 `gap_1.md` ~ `gap_6.md` |
| 주제별 대조 | 두 묶음을 주제 7개로 나눠 대조하고, 어긋난 곳을 판정 | 끝남. **반박 검증 전** | [`merged/`](merged/) |
| 반박 검증 | 대조 결과를 다른 사람이 따로 다시 계산해 확인 | **안 함** | |
| 통합 보고서 | 결론, 정할 것, 기획서 재료, 시연 계획을 한 문서로 | **안 함** | |

## 지금 있는 것을 어떻게 읽나

처음 보는 사람은 이 순서로 읽는다.

1. [`merged/overview.md`](merged/overview.md): 주제 7개의 결론과 결정별 추천만 모은 짧은 문서다. 여기부터 본다.
2. [`merged/summary.md`](merged/summary.md): "팀이 정할 것"(46건)의 선택지와 근거, "두 조사가 달랐던 곳"(82건), "확인하지 못한 것"(95건)을 모은 표다. 길다. 정할 항목을 찾아 그 줄만 본다.
3. [`merged/`](merged/)의 주제별 문서 가운데 자기가 맡은 부분. 주제마다 "쓸 값" 표가 있다. 주제 문서가 가리키는 `files/` 는 [`merged/files/`](merged/files/)에 있는 재계산 스크립트와 출력이다.
4. 수치의 근거를 확인해야 할 때만 [`prestudy/`](prestudy/)와 [`asos-report.md`](asos-report.md).

## 읽을 때 주의할 것

- **주제별 대조 결과는 한 번도 반박 검증을 받지 않았다.** 앞 단계들은 검토에서 실제로 틀린 것이 여러 건 잡혔다(급락을 "하루 사이"라고 과장한 것, 날씨 열이 하루 밀린 것 등). 대조 결과에도 그런 것이 남아 있을 수 있다. 특히 "한쪽 조사가 틀렸다"는 판정은 정의나 기간이 달라 둘 다 맞는 경우일 수 있다.
- **주제끼리 맞춰 보지 않았다.** 주제 7개는 서로의 결론을 모르고 따로 진행됐다. 한 주제의 권고와 다른 주제의 권고가 함께 성립하지 않을 수 있다. 가장 눈에 띄는 것은 두 번째 입력과 시연 구간이다. 실제 예보 자료는 2022-07 이후에만 있고, 출력이 떨어진 사건은 2021년 5월이다. 드리프트 주제는 시연을 두 장면으로 나누는 안을 냈는데, 그 안이 다른 주제의 추천(업로드 파일, 게이트)과 함께 성립하는지는 아무도 확인하지 않았다.
- **수치는 모두 조사 단계의 값이다.** 발표에 쓸 결과는 우리 서버로 직접 돌려 얻는다.
- **예측 시점에 받을 수 없는 값을 쓴 수치**(대상일의 실제 관측 날씨를 넣은 결과)는 "상한"이다. 문서에 그렇게 표시돼 있으니 인용할 때 표시를 떼지 않는다.

## 이어서 할 일

급한 순서다. 1번과 4번은 사람이 한다. 2번과 3번은 AI 에이전트에게 맡길 수 있다.

1. **팀이 정한다.** [`merged/summary.md`](merged/summary.md)의 "팀이 정할 것"을 보고 정한 뒤 [`../decisions/`](../decisions/)에 한 건씩 적는다. 서로 묶인 것(두 번째 입력과 시연 구간, 예측 시점과 제출 시각, 판정 방법과 고칠 코드)은 함께 정한다.
2. **결정에 걸린 수치를 반박 검증한다.** 전부 할 시간이 없으면 정한 값의 근거가 된 수치만 한다. 아래 "반박 검증 지시문"을 쓴다.
3. **통합 보고서의 앞부분을 쓴다.** 아래 "보고서 지시문"을 쓴다. 시간이 없으면 건너뛰고 기획서를 바로 써도 된다. 기획서 항목별 재료는 주제별 문서에 이미 있다.
4. **확인하지 못한 것을 옮긴다.** [`merged/summary.md`](merged/summary.md)의 "확인하지 못한 것"을 [`../followups.md`](../followups.md)로 옮기고, 항목마다 기획서에서 어떻게 다룰지(가정으로 명시, 범위 밖으로 선언)를 붙인다.

## 저장소에 없는 것

조사할 때 쓴 재계산 스크립트와 중간 결과(수백 MB)는 대부분 넣지 않았다. 박상명의 Mac 에 있다. 저장소에 있는 것은 최종 데이터 파일, 원본 3종, 데이터를 만든 스크립트, 그리고 주제별 대조에서 쓴 재계산 스크립트와 출력([`merged/files/`](merged/files/))이다. 스크립트에는 원래 작업 폴더의 경로가 적혀 있어 그대로는 실행되지 않는다. 반박 검증은 [`../../datasets/raw/`](../../datasets/raw/)의 원본과 [`../../datasets/hadong_daily_full.csv`](../../datasets/hadong_daily_full.csv)에서 다시 계산하는 것으로 한다. 실습 LSTM 학습을 다시 돌려야 하는 수치는 시간이 걸리므로 꼭 필요한 것만 한다.

## 반박 검증 지시문

주제 하나에 한 번씩 쓴다. `{주제 파일}` 을 `docs/research/merged/` 의 파일 이름으로 바꾼다.

```text
당신은 조사 결과를 검증하는 사람입니다. docs/research/merged/{주제 파일} 을 그대로 믿지 말고 반박하려고 시도하세요.

배경: 이 저장소는 태양광 발전소의 다음 날 하루 발전량을 예측하는 모델을 서빙하고 드리프트를 감지하는 조별 프로젝트입니다. 서로 모르고 진행된 두 묶음의 조사(docs/research/prestudy/ 와 docs/research/asos-report.md)를 주제별로 대조한 결과가 docs/research/merged/ 에 있고, 아직 아무도 다시 확인하지 않았습니다. docs/research/handoff.md 를 먼저 읽으세요.

할 일:
- "두 조사가 달랐던 곳"의 판정을 하나씩 다시 봅니다. 판정이 걸린 수치는 datasets/raw/ 의 원본과 datasets/hadong_daily_full.csv 에서 직접 다시 계산합니다. 문서가 근거인 판정은 출처를 직접 열어 대조합니다. "한쪽이 틀렸다"는 판정은 정의나 기간이 달라 둘 다 맞는 경우가 아닌지 특히 의심합니다.
- "쓸 값" 표는 중요한 것부터 근거 문서를 열어 수치, 날짜, 이름, 조건이 같은지 봅니다.
- 두 묶음의 원 자료를 직접 읽고, 같은 대상을 다르게 말하는데 표에 없는 것을 찾습니다.
- 예측 대상일의 실제 관측처럼 예측 시점에 받을 수 없는 값을 쓴 수치가 표시 없이 쓰였는지 봅니다.
- "팀이 정할 것"의 추천이 근거 수치에서 실제로 따라 나오는지 봅니다.

지킬 것:
- 수치는 자료에 있는 값이거나 직접 실행한 스크립트에서 나온 값만 씁니다. 추정은 추정이라고 밝히고, 확인하지 못한 것은 확인하지 못했다고 씁니다.
- project/ 의 코드는 읽기만 합니다. docs/research/prestudy/ 와 asos-report.md 는 고치지 않습니다.
- 계정 만들기, 로그인, API 키 입력은 하지 않습니다.
- 새로 쓴 스크립트는 tools/verify/ 에 둡니다.

결과: 같은 파일을 고치고, 맨 끝에 "## 반박 검증에서 고친 것" 절을 두어 무엇을 왜 고쳤는지와 다시 확인하지 못한 것을 적습니다. 고친 것이 없으면 없다고 씁니다.
```
