# 보완 조사 2: 두 번째 입력(일사량 예보)의 자료 기간과 드리프트 시연 구간이 겹치지 않는다

검토자가 다시 돌려 고친 결과다.

## 왜 조사했는가

D2가 권한 두 번째 입력(하루 전 일사량 예보)은 2022-07-03 이후에만 있고, D3가 권한 시연 구간(2021년 5월 중순 하락)은 그 전이다. 2021년을 덮는 예보는 GSM 구름양(2016년~)뿐이다. 예보를 넣은 모델에서 실제 사건이 오차나 치우침으로 드러나는지는 아무도 재지 않았다(D3의 날씨 모델은 대상일 실제 일사량을 쓴 상한이다). 실습 코드의 batch_test는 값 하나(prices)만 받고 두 번째 입력을 상수 SIMULATED_VOLUME = 1,200,000으로 채우며 schemas.py의 volume은 int라서, 예보를 쓰면 시연 경로를 고쳐야 한다. 또 '24시간 전 예보'의 정의가 3b(블로그로 24~26시간째 단계라고 확인)와 D2(확인하지 못함)에서 엇갈려, 거래 전일 10시·17시·20시 제출에 실제로 쓸 수 있는 값인지 정리되지 않았다. 두 번째 입력과 시연 구간은 팀이 가장 먼저 정해야 하는 두 결정인데 서로 묶여 있다.

### 미래 정보에 대해

원 분석이 표시하지 않은 미래 정보 사용은 새로 찾지 못했다. 원 분석이 스스로 표시한 것은 그대로 남아 있고, 검토에서 그 크기를 쟀다.

1. GSM 구름양 하루 전 예보(07 ~ 18시 평균)는 전날 15시와 21시(KST)에 초기화된 실행분이 섞인 값이다. 원 분석이 미래 정보로 표시했다. 검토에서 전날 09시 실행분의 값(대상일 09시 칸)만 두 번째 입력으로 써서 다시 재니 학습 RMSE 가 55.6kWh 에서 64.8kWh 로 올랐다. 2021년 하락이 오차에 드러나지 않는다는 결론은 같았다(드리프트 구간 0.93배, 치우침 +1.7kWh).
2. 대상일 재분석 일사량을 넣은 상한 모델은 의도한 상한이고 원 분석이 그렇게 표시했다.
3. 일사량 예보(MSM 하루 전)의 하루 합계는 미래 정보가 아니다. 검토자가 Single Runs 응답과 따로 대조하니 양수인 13칸이 모두 전날 00UTC 와 전전날 12UTC 실행분의 값이었고, 2022-07 ~ 2026-02 보관 자료에서 하루 합계의 96.78% 가 KST 09 ~ 20시(전날 09시 실행분), 3.22% 가 00 ~ 08시(전전날 21시 실행분), 0.000% 가 21 ~ 23시였다. 다만 이 판단은 예측 시점이 전날 저녁이라는 전제에 선다. 17시 제출에서는 전날 일합계가 아직 끝나지 않았고, 00UTC 실행분의 배포 지연은 재지 못했다.
4. 시간 순서를 무시한 분할은 없었다. 모델, 포락선, 같은 계절 비는 모두 사건 전 기간으로만 맞췄고 대리 모형은 스케일러를 쓰지 않는다. 성능 지표의 기대식은 검토자가 2013-01-01 ~ 2014-12-31 의 728일로 다시 맞춰 파일의 값과 최대 0.0005kWh 차이임을 확인했다. 정지 관문의 7일 창과 갱신 기준선은 과거 쪽만 본다.
5. 미래 정보는 아니지만 기준이 오염된 곳이 있다. 구간 B 와 N2 의 기준 기간(2023-11-07 ~ 2025-02-28)에 2024-07-10 ~ 18 의 절반 출력 9일이 들어 있다. 이 9일을 빼면 예보 비율 규칙의 N2 하락 오경보가 4회(20일)에서 9회(27일)로, 21건 RMSE 1.3배 규칙(일사량 예보 모델)의 N2 오경보가 4회(32일)에서 15회(64일)로 달라진다.
6. 기준값을 고른 구간과 성능을 센 구간이 같다(원 분석이 밝힘). 천장 규칙의 한도 0.90 은 2021년 사건과 N1, N2 를 보고 고른 값이고, 성능 지표의 7.5%, 30일, 3일 연속은 2013 ~ 2025 전체를 보고 고른 값이다. 한도를 0.88 로 바꾸면 2021년 지연이 13일에서 26일로 늘고, 0.92 로 바꾸면 N1 오경보가 1회 생긴다.

### 만든 파일 점검

이 과제는 업로드용 데이터 파일을 만들지 않았다. 만든 결과 파일과 받아 둔 응답을 대조한 결과는 다음과 같다.
- c1_table.csv(판정 방법 비교 표, 17행): 스크립트 사본을 다시 돌린 파일과 바이트 단위로 같았다. 방법마다 고른 칸은 lib.py 를 쓰지 않는 코드로 원자료(data_15043409.csv, wx_prevruns_hourly.csv, hadong_daily_full.csv)에서 다시 세어 같은 날짜와 횟수가 나왔다. (a) 는 사건 5건과 N1, N2 전부, (b) 는 사건 4건과 N1, N2, (c) 는 2024년 사건 2건과 N2, (d) 는 2015-01, 2021-05, 2024 봄과 N1, N2 다.
- s3_stats_B915.csv(552행)와 s3_alarms_B915.csv(8,004행): 다시 돌린 파일과 바이트 단위로 같았다. 따로 쓴 코드로 일사량 예보 모델과 두 번째 입력 없는 모델의 30일 RMSE 중앙값, 치우침 중앙값, 규칙별 30일 안 감지율(×1.0, ×0.915, ×0.86, ×0.70)을 다시 계산해 같은 값을 얻었다.
- hadong_daily_full.csv(ASOS 묶음의 파일, 이 과제가 읽어 쓴 것): gen_kwh 가 원자료 총량과 차이 0 이었다. 기대 발전량 열은 2013 ~ 2014 의 728일로 다시 맞춘 값과 최대 0.0005kWh 차이였고, 정지 49일, 보류 68일, 판정에 쓰는 날 4,658일(2025-12-31 까지)이 같았다. pi_21d 와 pi_30d 는 다시 합한 값과 최대 0.00005 차이(반올림)였다.
- api 폴더의 메타 파일 5건: 초기 시각과 공개 시각의 차이를 다시 계산해 5.06, 5.13, 9.57, 9.57시간을 얻었다. 검토 중 새로 받은 메타 파일에서 21UTC 실행분의 지연은 3.52시간이었다.
- Single Runs 와 Previous Runs 응답: MSM 일사량의 previous_day1 13칸과 previous_day2 13칸이 원 분석이 말한 실행분의 값과 같았다. GSM 응답 4건은 따로 대조하지 않고 원 출력만 읽었다.
- result.json: 항목 13개의 상태와 미래 정보 표시가 검토 대상으로 받은 내용과 같았다.

### 검토자 의견

재현 여부
- 원 분석의 수치는 모두 재현됐다. 스크립트 사본 14개(s1, s1b, s2, s3, s3b, s4, s5b, s5c, s7, s8, c1, c2, c3, v0)를 다시 돌려 출력이 같았고, lib.py 를 쓰지 않는 코드로 핵심 수치를 원자료에서 다시 계산해 같은 값을 얻었다.
- 틀린 계산은 찾지 못했다. 고친 것은 빠뜨린 대조와 과장으로 읽힐 표현이다.

고친 곳 다섯 가지
1. 예보 비율 규칙은 주입 없이도 시작일의 26% 에서 30일 안에 켜진다. 원 분석의 출력에 있던 값인데 결과 요약에는 빠져 있었다. 기준 기간에 든 절반 출력 9일(2024-07-10 ~ 18)을 빼면 주입 없음 35%, 한 해 하락 오경보가 4회에서 9회가 된다.
2. 천장 규칙의 '2021년 13일, 오경보 0회'는 N1 과 N2 에만 해당한다. 같은 포락선으로 2018-08 ~ 2020-09 에 7회(41일) 켜졌고, 한도 0.88 이면 지연이 26일이다. 2024-07 의 '9일'은 사건이 끝난 다음 날 하루만 켜진 경보다.
3. MSM 21UTC 실행분의 배포 지연은 3.52시간이었다. 원 분석의 조회가 공개 4초 전이었다. 지연 표본은 3.5 ~ 5.1시간의 3개가 됐고 00UTC 실행분은 여전히 재지 못했다.
4. 'GSM 개정으로 인한 구름양 이동이 2021년 비율 지표를 올렸다'는 설명은 추정으로 낮췄다. 같은 이동이 이어진 2022년의 같은 날짜 비율은 1.031 이었다.
5. 구간 B 의 학습 표본에서 절반 출력 9일이 걸린 29건을 빼면 21건 RMSE 1.3배 규칙의 N2 오경보가 4회(32일)에서 15회(64일)가 된다. 배수 기준이 학습 구간의 이상일에 민감하다는 뜻이다.

검토에서 보탠 실험
- 실습 LSTM: 원 분석은 LSTM 을 돌리지 않았다(모두 선형 대리 모형). 다시 학습할 원 LSTM 이 없어서, 핵심 결론 두 가지(일사량 예보 × 2024년 사건, 일사량 예보 × 주입)를 시드 3개(42, 1, 2)로 새로 학습해 방향만 확인했다. 조건마다 100 epoch, 학습 467건과 480건이다. 결론은 같은 쪽이었다. 시드 3개는 범위를 가늠하는 정도이고 평균과 편차를 말하기에는 적다.
- 미래 정보를 뺀 구름양 입력(전날 09시 실행분의 값)으로 2021년 실험을 다시 쟀다. 원 분석이 하지 못했다고 적은 '제출 시각에 받을 수 있는 구름양 예보'의 한 가지 대안이다. 이틀 전 값으로는 재지 않았다.
- 성능 지표 정책을 ASOS 보고서 2.4절과 2.5절의 글만 보고 따로 구현해 경보 6건이 같음을 확인했다.

다시 돌리지 않았거나 확인하지 못한 것
- s5_input_drift.py(연도별 통계), s6_runs.py, s6b_blocks.py, v1, v2, v3, rerun_s0_check 는 출력만 읽었다. MSM 의 실행분 대조는 따로 했고 GSM 의 대조는 따로 하지 않았다.
- 일본 기상청 공지문은 저장된 10건 가운데 4건(제557, 606, 575, 648호)만 열어 봤다. GitHub 이슈 파일과 전력시장운영규칙 원문은 열어 보지 않았다. 제출 시각은 사전 조사의 값 그대로다.
- ASOS 의 LSTM 실험과 다른 보완 과제의 LSTM(solar/g1_lstm)은 다시 돌리지 않았고 기록만 읽어 인용 수치가 맞는지 봤다.
- MSM 00UTC 실행분의 배포 지연은 검토 시각(01:06 UTC)에 아직 공개 전이라 재지 못했다.
- 성능 지표에 수준 주입을 하는 실험은 하지 않았다. 주입 시연의 판정 지표로 성능 지표를 쓰려면 따로 재야 한다.
- 실습 LSTM 에 상수를 넣는 실험(코드 제약 3번)은 대리 모형 값만 있다.

다른 설명과 한계
- 사건은 방법마다 한 번씩만 관측된다. 지연 일수의 차이(예: 13일 대 33일)에 통계적 의미를 두기 어렵다.
- 주입 시작일 46개는 한 해 안의 7일 간격이라 서로 겹친다. 백분율은 그 한 해의 몫이다.
- 기준값을 고른 구간과 성능을 센 구간이 같다(천장 규칙의 0.90, 성능 지표의 7.5%, 30일, 3일 연속). 원 분석이 밝혔고 검토에서 한도별 민감도를 보탰다.

- 영향: 기획서의 운영 설계(배포 게이트는 예측 오차, 드리프트 판정은 수준 지표로 분리)와 동작 화면의 시연 순서를 정할 수 있다. 시연 화면에 쓸 수준 지표를 예보 비율로 할지 천장 규칙으로 할지는 오경보율(한 해 4 ~ 9회 대 0회)과 필요한 자료(예보 대 시간대별 발전량)를 놓고 팀이 정해야 한다.

## 하지 않은 것

- 실습 LSTM 으로 예보 입력 조합을 다시 재지 않았다. 이 과제의 모델 수치는 모두 선형 회귀 대리 모형 값이다. LSTM 측정은 다른 보완 과제의 범위다.
- 제출 시각에 받을 수 있는 구름양 예보(GSM 이틀 전 값)로 2021년 실험을 다시 재지 않았다. 10년 치 시간별 자료를 새로 받아야 한다.
- MSM 00UTC 실행분의 Open-Meteo 배포 지연을 직접 재지 못했다. 메타 파일은 가장 최근 실행분만 보여 주고, 확인한 것은 06UTC 와 18UTC 실행분이다.
- Open-Meteo 문서의 '2018년부터'와 실제 시작일(GSM 2016-01-02, MSM 2022-07-02)이 다른 이유를 다 찾지 못했다.
- 성능 지표에는 수준 주입을 하지 않았다. ASOS 의 실험을 다시 하지 않는다는 조건 때문이다. ×0.915 비교는 예보 비율과 천장 규칙, 모델 오차 규칙에만 있다.
- 2026-01 ~ 02 의 성능 지표는 광양 ASOS 자료가 없어 계산하지 못했다(가입이 필요함). 그래서 변화 없던 구간 N2 를 2025-12-31 에서 끊었다.
- 민감도 실험(s8, 릿지와 그래디언트 부스팅)은 다시 돌리지 않고 어제 출력만 읽었다.
- 전력시장운영규칙 원문을 다시 열어 제출 시각을 확인하지 않았다. 사전 조사 4a, 4b 의 값을 그대로 썼다.
- 설비 용량, 정지일 목록, 게이트 기준의 차이는 이 과제에서 다루지 않았다. 정지일은 방법 (b), (c), (d) 에 D3 의 50일을, (a) 에 ASOS 의 정지 관문을 그대로 썼다.
