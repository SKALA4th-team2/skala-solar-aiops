LSTM 원 예측 파일·모델과 위성 전기간 원본은 저장소에 없어 기존 RMSE·시드별 결과는 원 조사 수치로 유지하며 독립 재현했다고 주장하지 않는다. 아래의 `확인 여부`는 원대조의 표시이고, 이번 유지/수정/재확인불가 판정은 끝 절에 있다. `(작업 폴더)`·`solar/`·`asos/`·`merged/gap1/` 경로는 원 조사자의 외부 작업 폴더이며 현재 저장소 파일 경로가 아니다. 저장된 대조 스크립트와 출력은 `files/` 아래에 있다.

## 날씨 자료와 두 번째 입력

두 번째 입력(실습 LSTM, 곧 수업에서 받은 실습 코드의 예측 모델이 발전량과 함께 받는 둘째 값이고 원래 코드의 Volume 자리)은 대상일(맞히려는 날, T)에 대한 24시간 전 일사량 예보로 정하고, 운영 모델의 업로드 파일은 `hadong_upload_forecast_jma.csv` 를 쓴다. 이 예보를 넣은 실습 LSTM 의 RMSE(예측과 실제의 차이를 제곱해 평균한 뒤 제곱근을 취한 값, 단위는 하루 kWh)는 42 ~ 46kWh 로 발전량만 넣은 77 ~ 79kWh 보다 낮고, 지난 관측은 넣어도 효과가 없으며(79.2 대 78.5kWh), 대상일의 실제 관측을 넣은 23kWh 는 예측 시점에 받을 수 없는 값이라 '예보가 완벽하다면'을 보이는 시연과 사후 감시에만 쓴다. 기상청 광양 관측소의 일사량과 Open-Meteo(키 없이 쓰는 공개 날씨 API)의 재분석 일사량(관측과 수치 모델을 합쳐 다시 계산한 격자 값)은 같은 날 상관 0.947, 차이의 RMSE 2.37MJ/m2(관측 평균의 15.7%)로 맞고, 위성 영상에서 계산한 일사량은 관측과 상관 0.981 로 더 가깝다.

파일 경로는 모두 `(작업 폴더)` 아래의 상대 경로다. 원대조 스크립트와 출력은 `files/T3-weather-input/` 에 있고, 이번 독립 계산은 `tools/verify/verify_t3t4.py` 로 재현한다.

이 절에서 쓰는 말은 다음과 같다.

- ASOS 는 기상청의 종관기상관측이다. 하동군에는 일사량을 재는 관측소가 없어 광양시(지점 번호 266) 값을 빌려 쓴다. 발전소까지 약 14.5km 다(발전소 위치를 가정한 추정).
- 재분석은 관측과 수치 모델을 합쳐 과거 날씨를 격자로 다시 계산한 자료다. Open-Meteo 보관 자료는 2016년까지 ERA5, 2017년부터 ECMWF IFS 값이다.
- 위성 일사량은 히마와리 위성 영상에서 계산한 지표 일사량이다.
- 24시간 전 예보는 Open-Meteo Previous Runs 의 `_previous_day1` 고정 lead time 자료다. 개별 실행분 전체를 전날 같은 시각에 한 번 받은 자료와는 구분한다. 업로드 원본은 `models` 를 지정하지 않은 Best Match 호출이다. 2026-10의 표본에서는 일본 기상청 MSM 값과 일치했다. JMA 고정 호출은 `models=jma_msm` 또는 `models=jma_seamless`, 전 지구 모델은 `models=jma_gsm` 으로 구분한다. Best Match 전체 기간을 순수 JMA 값으로 단정하지 않는다. GSM 은 같은 기관의 전 지구 모델이고 일사량은 주지 않는다.
- 하늘상태는 기상청 단기예보의 구름 정도 항목(맑음, 구름많음, 흐림)이다.
- 상한은 대상일의 실제 날씨를 입력에 넣은 실험, 곧 예보가 완벽하다고 가정한 값이다.
- 규칙은 학습 없이 "최근 7일의 (발전량 합 ÷ 일사량 합) × 대상일 일사량"으로 내는 예측이다.

**운영에서 쓸 수 있는 입력**

- 대상일에 대한 24시간 전 일사량 예보. 공개 시각이 추정이므로 여유를 두어 전날 15시 이후에 받는다.
- 대상일에 대한 48시간 전 일사량 예보. 전날 오전 입력의 보수적 후보로 두되, 발전량도 T-2 까지인 조건의 조합 성능은 별도로 검증한다.
- 기상청 단기예보의 하늘상태. 가입이 필요하고, 실제 예보를 넣은 성능은 아무도 재지 못했다.
- T-2 까지의 관측 날씨. 쓸 수는 있지만 효과가 없다.

**시연이나 사후 감시에만 쓸 수 있는 입력**

- 대상일의 광양 관측 일사량과 일조 시간(`hadong_upload_forecast_proxy.csv`). 화면에 "예보가 완벽하다고 가정"이라고 적는다.
- 대상일의 재분석 일사량과 위성 일사량.
- JMA GSM 구름양 예보의 보관 값. 2021년 구간을 덮는 유일한 예보지만 전날 저녁에 받을 수 없는 값이 섞여 있다.
- Open-Meteo Historical Forecast API 에서 사후 조회한 대상일 자료와 historical `_previous_day0` 값. 짧은 lead time 예보를 이은 값이므로 전날 저녁에 받을 수 있던 24시간 전 예보를 대신할 수 없다. 실제 관측값 자체라는 뜻도 아니다. 운영 당시에 수신·보관한 최신 예보는 수신 시각이 입증되는 범위에서 운영 입력으로 사용할 수 있다.

## 반박 검증에서 고친 것

1. **예보 출처와 운영 조건을 구분했다.** 실제 수집 스크립트는 `models` 를 지정하지 않은 Best Match 이다. `JMA MSM` 은 표본 대조 결과이고 전기간 순수 JMA 를 뜻하지 않는다. 고정 모델 요청명은 `jma_msm`, `jma_seamless`, `jma_gsm` 이다. GSM 은 일사량을 제공하지 않는다. 모델 선택·lead time 이 다른 최신 Forecast API 로 운영해도 42~46kWh 가 그대로 나온다는 약속을 삭제했다. [공식 JMA 문서](https://open-meteo.com/en/docs/jma-api), [Previous Runs 문서](https://open-meteo.com/en/docs/previous-runs-api).
2. **실측 범위가 모두 겹친다는 판정을 고쳤다.** 42~46kWh 와 46.7~51.5kWh 는 겹치지 않는다. 모델·구간이 다른 값의 차이만으로 한 조사 오류를 판정하지 않는다. LSTM 숫자는 원 예측이 없어 독립 재현하지 못했다.
3. **결측 구간의 ICON 단정을 추정으로 낮췄다.** 보관 JSON 에서 2024-02-01~02-02 낮 24칸은 Best Match=ICON 이고 JMA 3모델은 모두 결측임을 직접 계산했다. 전체 약 23일·534시간의 출처를 확인한 응답은 저장소에 없다. 본문·표·부록의 단정과 끝 절의 미확인이 서로 맞도록 고쳤다.
4. **예보 실행분과 가용 시각의 한계를 보탰다.** 원 조사 이틀 표본의 07~08시 값은 그 전날 21시 실행분, 09시 이후는 전날 09시 실행분이다. 따라서 하루 합계를 전날 09시 단일 실행분이라고 표현하지 않는다. 보관 메타로 직접 계산한 MSM 지연 3.5203시간(같은 실행분 사본 2개), GSM 지연 9.5664시간은 특정 실행분의 값이고, 오전 09시 MSM 실행분의 공개 시각은 재지 못했다. 초기화 시각과 공개 시각은 다르다. [Single Runs 문서](https://open-meteo.com/en/docs/single-runs-api), [갱신 안내](https://open-meteo.com/en/docs/model-updates).
5. **오전 조건을 분리했다.** 48시간 전 예보로 서빙 입력만 바꾼 실험은 발전량 T-1 창을 유지한다. 오전에 발전량 T-2 까지만 아는 조건과 조합한 RMSE 라고 부르지 않는다.
6. **관측 누수 표시는 유지했다.** 상한 파일은 T 뿐 아니라 T-1 ASOS 도 공개 전 값이다. ASOS 를 예보로 바꿔 서빙하는 배치는 T-1·T 둘 다 교체해야 한다. 포털은 전일 자료가 당일 10시 이후라고 명시한다. API 의 11시 안내는 원 조사 활용가이드가 저장소에 없어 이번에 다시 확인하지 못했다. API 페이지는 전일까지만 제공하며 인증키가 필요함을 확인했다. [ASOS 포털](https://data.kma.go.kr/data/grnd/selectAsosRltmList.do?pgmNo=36), [API 정보](https://www.data.go.kr/data/15059093/openapi.do).

이번 계산은 `python3 tools/verify/verify_t3t4.py --root .` 로 재현한다. 표준 라이브러리만 사용하고 프로젝트 코드를 import 하지 않는다. 출력은 `tools/verify/verify_t3t4.log` 에 보관한다. 원본 `datasets/raw/data_15043409.csv` 4,807일과 `hadong_daily_full.csv` 발전량은 최대차 0, 시간별 24칸 합과 원본 총량의 최대차는 1.14e-13kWh 였다. 로그인·API 키·계정은 사용하지 않았다. 날짜별 LSTM 원 예측, 원 모델, 위성 전기간 응답, 원 ASOS·날씨누리 연도별 자료가 없어 그 수치들을 독립 재현하지 못했다. 기존 스크립트의 외부 폴더 경로 및 `t4_preds.pkl` 부재 때문에 기존 스크립트를 그대로 재실행했다고 주장하지 않는다.

**전체 행 스케일 점검.** 프로젝트 baseline 은 분할 전에 전체 행으로 scaler 를 맞춘다(`project/scripts/train_baseline_v1.py:68`). 일반적인 평가에서는 시험 자료의 최솟값·최댓값이 섞일 수 있는 절차다. 다만 이번 세 파일은 앞 학습행과 전체행의 Close·Volume min/max 가 모두 같았다. 예보 파일은 Close 5.886~338.832kWh, Volume 0.9504~28.3608MJ/m2, ASOS 두 파일은 Close 0~379.752kWh, Volume 0.17~31.40MJ/m2 였다. 따라서 이 세 파일에 한해 전체 fit 때문에 정규화 수치가 달라진 누수 영향은 발견하지 못했다. 이것을 다른 파일·다른 분할에도 누수가 없다는 보증으로 확장하지 않는다.
