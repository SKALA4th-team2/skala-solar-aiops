# 0007: 설비 이상과 모델 품질 저하의 분기, 정지일의 처리, 알림

> 구현 적용: 이 제안의 채택 범위와 추가 보호 조건은 [0013](0013-backend-aiops-implementation.md)에 기록했다. 기존 제안 본문은 설계 이력으로 보존한다.

- 상태: 제안
- 날짜: 2026-10-07
- 정한 사람: (아직 없다. 팀이 확정할 때 적는다)

## 배경

HAIC 스켈레톤은 드리프트로 판정되면 곧바로 재학습한다(`serving_app/monitoring/retrain_trigger.py` 의 `check_and_trigger`). 알림은 `logs/aiops.log` 에 `[WARN] drift detected - triggering retrain` 한 줄을 남기는 것이다. 대시보드는 사람이 로그 단추를 눌렀을 때 그 파일의 내용을 보여 준다.

태양광에서는 "예측이 틀렸다"의 원인이 둘로 갈린다.

- 설비가 멈췄거나 일부만 돌고 있다. 며칠 뒤 고쳐지면 원래 수준으로 돌아온다. 이 구간으로 모델을 다시 학습시키면 모델이 잘못된 수준을 배운다.
- 발전소의 출력 수준이 바뀐 채로 이어진다. 원인이 설비든 오염이든 예측은 바뀐 수준을 따라야 한다.

두 경우에 할 일이 다르다. 앞의 것은 점검을 요청하고 재학습을 미룬다. 뒤의 것은 알리고 재학습을 검토한다. 그래서 둘을 가르는 규칙과, 각각에서 누구에게 무엇을 알릴지를 정해야 한다.

[결정 기록 README](README.md)의 "발전량 0 인 날과 정지일을 학습과 판정에서 어떻게 다룰지"가 이 기록의 범위다. 오차 계산에서의 처리는 [0003](0003-capacity-and-error-metrics.md)에 있다.

분기

| 선택지 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| (가) 가르지 않는다. 판정되면 재학습한다(현재 코드) | 고칠 것이 없다 | 정지 구간으로 재학습한다. 설비 담당자가 알 길이 없다 |

## 결정

다음을 제안한다.

**하루 단위의 규칙.** x 는 그날의 실제 발전량, e 는 그날의 관측 날씨로 계산한 기대 발전량이다.

| 이름 | 조건 | 쓰임 |
| --- | --- | --- |
| 정지 | x 가 0 이하이거나, e 가 30kWh 이상인데 x 가 e 의 30% 미만 | 판정과 재학습에서 뺀다 |
| 낮은 날 | 정지이거나, e 가 80kWh 이상인데 x 가 e 의 70% 미만 | 보류를 세는 데 쓴다 |
| 보류 | 그날까지의 7일에 낮은 날이 3일 이상 | 판정과 재학습에서 뺀다. 설비 점검 알림을 낸다 |
| 유효한 날 | e 가 있고 0 보다 크며, 정지도 보류도 아닌 날 | 성능 지표를 계산하는 날 |
| 하루 점검 알림 | e 가 80kWh 이상인데 x 가 e 의 50% 미만 | 그날 하루의 알림. 재학습과 무관하다 |

**배치 단위의 분기는 (나)** 로 한다. 위에서부터 차례로 본다.

1. 유효한 날이 15일에 못 미친다 → 판정하지 않는다. 대상 21일에 정지나 보류가 있었으면 "설비 점검 필요"를 알리고 **재학습을 미룬다.**
2. 뒤 21일의 성능 지표 편차가 −7.5% 아래다 → "출력 수준 저하"를 알린다. 설비 담당자에게 점검도 함께 요청한다. 앞 20일의 편차도 −7.5% 아래이면 **재학습 후보를 만든다**([0008](0008-retraining-and-version-switch.md)). 후보는 게이트를 통과해야 올라간다([0005](0005-deployment-gate.md)). 앞 20일이 아직 아래가 아니면 알리기만 하고 기다린다.
3. 21건 RMSE 가 보조 한도를 넘는다 → "입력 이상 의심"을 알린다. 재학습하지 않는다([0006](0006-monitoring-metric-and-thresholds.md)).
4. 그 밖 → 정상이다.

- 재학습에 쓰는 41행 안에 정지나 보류인 날이 있으면 재학습을 미룬다. 실습 코드는 행이 이어져 있다고 보고 창을 만들기 때문에 그 날만 빼고 학습할 수 없다.
- 정비로 수준이 돌아온 경우는 이 판정으로 잡지 못한다([0006](0006-monitoring-metric-and-thresholds.md)). 설비 담당자가 정비를 마쳤다고 알리면 운영자가 기준선을 다시 계산하고 재학습을 손으로 건다.

**알림은 (가)** 로 한다. 발표 범위에서는 `aiops.log` 의 문장과 대시보드의 로그 패널이 알림 창구다. 밖으로 보내는 알림은 만들지 않고 후속 과제로 적는다.

| 상황 | 알릴 사람 | 로그에 남길 문장(제안) |
| --- | --- | --- |
| 출력 수준 저하 | 서비스 운영자, 설비 담당자 | `[WARN] drift detected - triggering retrain` (기존 문장 그대로) |
| 수준 저하이지만 재학습은 기다림 | 서비스 운영자 | `[INFO] retrain waiting - input window not yet below limit (head_dev=..., tail_dev=...)` (새 문장) |
| 재학습 시작 | 서비스 운영자 | `[INFO] retrain triggered (window=last_21_days)` (기존 문장 그대로) |
| 게이트 통과와 승격 | 서비스 운영자 | `[OK] new_rmse=... - production promoted: HAIC_Predictor v...` (기존 문장 그대로) |
| 게이트 실패 | 서비스 운영자 | `[WARN] gate failed - production kept (new_rmse=..., limit=...)` (새 문장) |
| 설비 점검 필요, 재학습 보류 | 설비 담당자, 서비스 운영자 | `[WARN] facility check required - retrain held (outage_days=..., hold_days=...)` (새 문장) |
| 하루 점검 알림 | 설비 담당자 | `[WARN] daily output low - facility check suggested (date=..., ratio=...)` (새 문장) |
| 판정하지 않음 | 서비스 운영자 | `[INFO] monitor skipped - valid_days=... < 15` (새 문장) |
| 입력 이상 의심 | 서비스 운영자 | `[WARN] input anomaly suspected - rmse21=... > limit ...` (새 문장) |

기존 세 문장은 글자를 바꾸지 않는다. 교재와 대시보드의 안내문이 그 문장을 가리킨다.

## 다시 볼 조건

- 재학습 게이트가 잘못된 모델을 올리는 일이 확인될 때. (다)처럼 사람의 확인을 거치게 바꾼다
- 정비 기록을 받아 정지와 수준 변화의 실제 날짜를 알게 될 때. 한도(30%, 50%, 70%, 7일 가운데 3일)를 그 기록으로 다시 맞춘다
- 관측 날씨를 날마다 받을 수 없다고 확인될 때. 실적만 보는 정지 규칙으로 바꾼다
- 밖으로 보내는 알림 수단을 만들기로 할 때
