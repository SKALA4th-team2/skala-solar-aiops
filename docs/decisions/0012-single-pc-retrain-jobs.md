# 0012: 한 PC 에서의 재학습 작업 처리와 실행 단위

- 상태: 제안
- 날짜: 2026-10-07
- 정한 사람: (아직 없다. 팀이 확정할 때 적는다)

## 배경

FastAPI, 학습, MLflow, AIOps 를 PC 한 대에서 돌린다. 지금은 재학습이 배치 요청을 처리하는 프로세스 안에서 바로 돈다(`serving_app/monitoring/retrain_trigger.py` 의 `check_and_trigger()` 가 `fine_tune()` 을 부른다). 통합가이드도 이 점을 한계로 짚고 `BackgroundTasks` 를 개선안으로 든다.

발전소가 여럿이 되면 재학습이 걸리는 발전소도 여럿이 된다. 요청마다 학습을 돌리면 응답이 길어지고, 같은 발전소나 여러 발전소의 재학습이 한꺼번에 돌 수 있다. 재학습의 대기와 결과가 어디에도 남지 않아 서버를 다시 띄우면 흔적이 없다. [0008](0008-retraining-and-version-switch.md)은 "재학습이 도는 동안에는 새 재학습을 시작하지 않는다(서버 안의 잠금 하나)"를 제안했다. 이 기록은 그것을 발전소 여럿과 프로세스 여럿의 경우로 넓힌다.

## 검토한 선택지

| 선택지 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| (가) 지금처럼 요청 안에서 바로 돈다 | 코드가 가장 단순하다 | 요청이 재학습만큼 길어진다. 겹쳐 도는 것을 막지 못한다. 다시 띄우면 흔적이 없다 |
| (나) 같은 프로세스의 배경 작업과 프로세스 안의 잠금 | 응답이 바로 나간다. 고칠 곳이 적다 | 대기 중인 작업이 메모리에 있어 다시 띄우면 사라진다. 학습이 서빙과 같은 프로세스의 메모리와 CPU 를 쓴다. `uvicorn` 의 일꾼 수를 늘리면 잠금이 프로세스마다 따로다 |
| (다) 작업 기록(SQLite 파일)과 재학습 일꾼 프로세스 하나 | 대기와 결과가 파일에 남는다. 학습이 죽어도 서빙이 죽지 않는다. 잠금 파일 하나로 프로세스가 여럿이어도 겹침을 막는다 | 프로세스가 하나 는다. 승격을 서빙 프로세스에 알리는 길이 따로 필요하다 |
| (라) 메시지 브로커와 작업 큐 | 여러 PC 로 넓힐 수 있다 | 한 PC 의 범위와 교재의 범위를 넘는다 |

## 결정

다음을 제안한다.

- **(다)로 한다.** 서빙 프로세스는 재학습 조건이 채워지면 작업을 적고 바로 응답한다. 재학습 일꾼 프로세스 하나가 작업을 하나씩 꺼내 돌린다. 메시지 브로커는 들이지 않는다.
- **한 번에 하나만 돈다.** 발전소가 달라도 겹쳐 돌리지 않는다. 일꾼은 잠금 파일을 잡은 채로만 작업을 꺼낸다.
- **같은 재학습을 두 번 돌리지 않는다.** 작업은 `(plant_id, 종류, 자료의 끝 날짜)` 로 유일하다. 같은 요청이 또 오면 있는 작업의 상태를 돌려준다.
- **작업 기록은 MLflow 의 DB 와 다른 SQLite 파일에 둔다.** 상태는 `queued`, `running`, `succeeded`, `failed`, `skipped` 다. 작업의 번호를 로그와 응답에 싣는다.
- **다시 띄운 뒤.** 일꾼은 `running` 으로 남은 작업을 실패(중단됨)로 적고 다시 대기에 넣는다. 서빙 프로세스는 발전소별 감시 상태를 파일에서 읽는다.
- **승격은 파일로 알린다.** 일꾼이 승격한 뒤 발전소 폴더의 현재 버전 표시를 바꾸고, 서빙은 그 발전소의 요청 때 표시와 메모리의 버전을 견줘 다르면 새 모델을 먼저 불러온 뒤 상자를 바꾼다.
- **`uvicorn` 의 일꾼 수는 1 로 고정한다.** 모델 상자와 판정기의 상태가 프로세스의 변수이기 때문이다. 늘리려면 그 상태를 먼저 파일로 옮긴다.
- **메모리의 모델은 발전소별 상자에 두고 개수 한도를 둔다.** 기본 64개. 넘으면 가장 오래 쓰지 않은 모델을 내린다.
- **한도를 둔다.** 업로드 5MB·20,000행, 배치 요청 400행, 포트폴리오 요청 200곳. 출발점이고 백엔드 PC 에서 잰 뒤에 고친다.
- **로컬과 컨테이너는 파일을 나누지 않는다.** 로컬의 `project/` 를 컨테이너에 그대로 걸지 않는다. 응답과 로그에 실행 단위를 싣는다.
- **발표까지 시간이 없으면 (나)를 임시로 쓴다.** 일꾼 수 1 을 지키고 "다시 띄우면 대기 작업이 사라진다"를 적는다.

구조와 순서의 그림, 규모 산정식은 [한 PC 운영 문서](../proposal/single-pc-operation.md)에 있다.

## 근거

모두 조사에 쓴 PC(Apple M5, 코어 10개, 메모리 16GB)에서 발전소 한 곳(업로드 1,337행)으로 잰 값이다. 백엔드를 돌릴 PC 의 값이 아니다.

| 수치 | 조건 (기간, 분할, 시드 수) | 출처 |
| --- | --- | --- |
| 재학습 한 번이 4.4초(4.36, 4.35, 4.46초) | 최근 41행, 10 epoch. 측정 프로세스 안에서만 게이트를 열었다. 통과는 품질의 근거가 아니다 | [검증 M09](../proposal/evidence/multi-plant/validation.md#m09) |
| 처음 학습이 18.0초(최대 메모리 581MB), MLflow 학습이 22.0초(696MB) | 100 epoch 한 번씩 | [검증 M09](../proposal/evidence/multi-plant/validation.md#m09) |
| 예측 한 건의 계산 시간의 95번째 백분위: 한가할 때 13.7ms, 다른 프로세스가 학습할 때 16.1ms, 같은 프로세스의 다른 스레드가 학습할 때 21.9ms. 실패는 모두 0 | HTTP 를 거치지 않은 모델 계산 시간. 각각 200건, 1,540건, 1,299건 | [검증 M09](../proposal/evidence/multi-plant/validation.md#m09) |

## 다시 볼 조건

- 백엔드를 돌릴 PC 에서 같은 도구로 잰 값이 나왔을 때. 한도와 "한 번에 하나"를 다시 본다
- 재학습이 밀려 대기가 길어질 때. 발전소가 다르면 함께 돌리는 것을 검토한다
- `uvicorn` 의 일꾼 수를 늘려야 할 때
- PC 를 여러 대로 넓힐 때. 그때는 (라)를 본다
