# 0002: 입력의 뜻과 예측 시점

- 상태: API 입력 계약 확정 (#6 단건·CSV, #7 배치 적용), 운영 시점의 자료 수신은 기존 가정 유지
- 날짜: 2026-10-07
- 정한 사람: 사용자 (FastAPI 담당, 2026-10-07 대화에서 명세 9절 적용 승인)

## 배경

HAIC 스켈레톤의 모델은 최근 20거래일의 (종가, 거래량)을 받아 다음 날 종가를 낸다. 모양은 (20, 2) 이고 `data/features.py` 의 `SEQ_LEN = 20`, `serving_app/lstm_model.py` 의 `N_FEATURES = 2` 가 정한다. 이 모양을 유지한 채 두 값의 뜻을 태양광에 맞게 정해야 한다.

함께 정해야 하는 것이 예측 시점이다. 같은 입력이라도 언제 예측하느냐에 따라 받을 수 있는 값이 달라지고, 받을 수 없는 값을 넣은 성능은 운영 성능이 아니다.

정할 것은 다섯 가지다.

1. 두 번째 값으로 무엇을 넣는가
2. 언제 예측하는가
3. 어느 업로드 파일을 쓰는가
4. 파일의 열 이름과 API 의 필드 이름을 바꾸는가
5. 값의 범위와 날짜를 어디까지 검사하는가

## 검토한 선택지

두 번째 값

| 선택지 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| (가) 대상일에 대한 하루 전 일사량 예보(하루 합계, MJ/m²) | 예측 시점에 받을 수 있다고 보는 값 가운데 오차가 가장 작다 | 자료가 2022-07 이후에만 있다. 과거 예보가 당시 몇 시에 공개됐는지는 추정이다 |
| (나) 지난 관측 일사량(대상일 이틀 전까지) | 2013년부터 있다 | 조사에서 발전량만 넣은 것과 오차가 같았다 |
| (다) 대상일의 실제 관측 일사량 | 오차가 가장 작다 | 예측 시점에 받을 수 없다. 예보가 완벽하다고 가정한 상한으로만 쓸 수 있다 |
| (라) 두 번째 값을 쓰지 않는다(발전량만) | 날씨 자료가 필요 없다 | 조사에서 7일 평균보다 오차가 4 ~ 6% 낮을 뿐이었다 |

예측 시점

| 선택지 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| (가) 대상일 전날 20시 이후 | 전날 발전이 모두 끝난 뒤라 전날 하루 합계를 그대로 쓴다 | 제도의 1차·2차 제출 마감(전날 10시, 17시)보다 늦다. 시장 제출에 맞춘 시각이 아니다 |
| (나) 전날 17시 | 제도의 2차 제출 마감에 맞는다 | 전날 발전이 97.6%만 끝나 있어 잠정 합계를 보정해야 한다. 그 조건의 모델 성능은 아무도 재지 않았다 |
| (다) 전날 10시 | 제도의 1차 제출 마감에 맞는다 | 전날 발전량을 쓸 수 없고(15.8%만 끝남) 예보도 이틀 전 것을 써야 한다 |

이름

| 선택지 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| (가) `Date, Close, Volume` 과 `close, volume, predicted_close, prices` 를 그대로 두고 뜻과 단위를 문서와 필드 설명에 적는다 | 스키마, 업로드 검증, 대시보드, 시뮬레이션 스크립트를 조금만 고친다 | 이름과 뜻이 어긋나 처음 보는 사람이 헷갈린다 |
| (나) `generation_kwh`, `irradiance_forecast_mj` 처럼 이름을 바꾼다 | 이름이 뜻을 말한다 | 요청·응답 모양의 묶음(스키마, 라우터, 대시보드, 시뮬레이션, API 명세)을 한꺼번에 고쳐야 한다 |

## 결정

사용자가 다음 API 입력 계약의 적용을 승인했다. 단건 예측과 CSV 검증은 이슈 #6, 배치와 호출부는 #7에서 구현한다. 운영 시점의 자료 가용성은 아래에 명시한 가정이며 코드 구현으로 입증되지 않는다.

- **두 번째 값은 (가)** 대상일에 대한 하루 전 일사량 예보의 하루 합계(MJ/m²)다.
- **입력의 뜻.** 대상일을 T 라 하면 창은 T-20 일부터 T-1 일까지의 20행이다. d 일 행의 첫째 값은 d 일의 하루 발전량(kWh)이고, 둘째 값은 d+1 일에 대한 하루 전 예보다. 그래서 창 안의 발전량은 T-20 ~ T-1 일의 것이고, 예보는 T-19 ~ T 일에 대한 것이다. 창의 마지막 행에 대상일의 예보가 들어 있다. 20일은 거래일이 아니라 이어진 달력일이다.
- **예측 시점은 (가)** 대상일 전날 20시 이후다. 전날 하루 발전량을 그 시각에 받을 수 있다는 것과, 대상일 예보를 전날 15시 이후에 받을 수 있다는 것은 가정이다. 발표에서는 저장된 CSV 를 재생한다. 시장 제출 시각에 맞춘 것이 아니라고 적는다. (나)는 후속 확장으로 둔다.
- **업로드 파일은 `datasets/hadong_upload_forecast_jma.csv`** 다. 예보의 출처는 "Open-Meteo Previous Runs API, 모델을 지정하지 않은 호출(Best Match)"이라고 적는다. 파일 이름에 `jma` 가 있지만 전 기간이 일본 기상청(JMA) 자료라는 근거는 없다.
- **이름은 (가)** 그대로 둔다. 대신 `close` 는 0 을 받게 하고(`gt=0` → `ge=0`) `volume` 은 소수를 받게 한다(`int` → `float`). 필드 설명과 API 문서에 뜻과 단위를 적는다. (나)는 발표 뒤의 정리 과제로 둔다.
- **값의 범위.** 발전량은 0 이상 1,320kWh 이하, 일사량 예보는 0 이상 45MJ/m² 이하만 받는다. 1,320 은 55kW 가 24시간 내내 도는 양이고, 45 는 이 위도에서 대기권 밖 수평면이 하루에 받는 양의 연중 최댓값(41.5MJ/m²)보다 조금 큰 값이다. 정상 값을 거르려는 것이 아니라 단위를 잘못 넣은 값(Wh, W/m² 따위)을 거르려는 넓은 범위다.
- **날짜.** 요청의 점마다 날짜를 함께 받아, 20일이 하루씩 이어지는지 서버가 검사한다. 지금의 요청에는 날짜가 없어 순서와 빠진 날을 검사할 수 없다. 응답에 대상일을 실어 "어느 날의 예측인가"를 분명히 한다.
- **대상일의 실제 관측을 넣은 결과((다))는 주 시연에 쓰지 않는다.** 참고로 보일 때는 "예보가 완벽하다고 가정한 상한"이라고 적는다.

## 다시 볼 조건

- 전날 저녁에 그날 발전 실적을 받는 경로가 확인되거나, 받을 수 없다는 것이 확인될 때
- 과거 예보가 당시 몇 시에 공개됐는지 확인될 때. 전날 20시보다 늦었다면 조사 성능을 운영 성능으로 볼 수 없다
- 제도의 제출 시각(전날 10시, 17시)에 맞춘 예측을 범위에 넣기로 할 때
- 2021년 이전 구간으로 예측 모델을 시연해야 할 때. 그 기간에는 예보 자료가 없다
