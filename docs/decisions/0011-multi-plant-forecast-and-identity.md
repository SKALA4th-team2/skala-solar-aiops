# 0011: 여러 발전소의 예측 방식, 식별자, 평가

- 상태: 제안
- 날짜: 2026-10-07
- 정한 사람: (아직 없다. 팀이 확정할 때 적는다)

## 배경

발전소가 여럿이 되면 세 가지를 정해야 한다. 예측을 발전소마다 따로 할지 한꺼번에 할지, 발전소와 모델을 무엇으로 가리킬지, 품질을 무엇으로 잴지다.

지금의 코드는 발전소가 하나라는 전제로 짜여 있다. 업로드 폴더에서 가장 최근 파일 하나를 고르고, 스케일러와 모델의 경로와 레지스트리의 이름이 하나씩이고, 메모리의 모델 상자가 하나다. 찾은 곳의 목록은 [확장 문서 3절](../proposal/multi-plant-extension.md#3-지금-코드의-단일-발전소-가정)에 있다. HAIC 스켈레톤도 종목 하나였다.

## 검토한 선택지

예측 방식

| 선택지 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| (가) 발전소별 모델로 예측한 뒤 더한다 | 지금의 코드가 발전소 한 곳의 이 방식이다. 발전소별 게이트와 감시가 그대로 이어진다. 발전소마다 기간이 달라도 된다. 새 발전소는 그것만 학습한다 | 학습 횟수와 메모리의 모델 수가 발전소 수만큼 는다. 자료가 짧은 발전소는 게이트를 볼 수 없다 |
| (나) 여러 발전소를 함께 학습한 공통 모델 | 표본이 는다. 모델이 하나다. 새 발전소에 바로 쓸 수도 있다 | 용량이 다른 값을 한 모델에 넣도록 입력의 뜻과 스케일을 바꿔야 한다. 한 발전소가 왜 틀렸는지 가리기 어렵다. 배우지 않은 발전소에서의 성능을 따로 재야 한다 |
| (다) 포트폴리오 합계를 바로 예측한다 | 모델이 하나다 | 한 곳의 변화가 보이지 않는다. 모든 구성원이 값을 가진 날만 쓸 수 있다. 구성이 바뀌면 과거의 합계를 다시 만들고 처음부터 학습한다 |

기존 요청의 처리

| 선택지 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| (가) `plant_id` 를 선택 항목으로 더하고 없으면 기본 발전소로 본다 | 지금의 요청, 대시보드, 시연 스크립트, 테스트가 그대로 돈다 | 발전소를 빠뜨린 요청이 조용히 기본 발전소로 간다 |
| (나) `plant_id` 를 처음부터 필수로 한다 | 대상이 늘 분명하다 | 방금 맞춘 호출부와 테스트를 모두 고쳐야 한다 |
| (다) 경로를 새로 만들고(`/plants/{plant_id}/predict`) 기존 경로를 그대로 둔다 | 기존 계약을 건드리지 않는다 | 같은 일을 하는 경로가 둘이 된다 |

## 결정

다음을 제안한다.

**예측은 (가)로 한다.** 발전소마다 모델과 스케일러를 따로 두고, 포트폴리오의 값은 같은 대상일의 발전소별 예측을 더해 낸다.

- (나)는 발전소가 많아지고 자료가 짧은 새 발전소가 자주 들어올 때 다시 본다. 고를 때는 발전소 하나를 통째로 빼고 학습해 그 발전소에서 재는 평가를 반드시 한다.
- (다)는 쓰지 않는다.

**식별자**

- 발전소는 `plant_id`, 묶음은 `portfolio_id` 와 구성 버전으로 가리킨다. 모양은 영문 소문자, 숫자, 붙임표 2 ~ 40자다. 하동하수처리장은 `hadong-sewage` 다.
- 레지스트리의 모델 이름은 `solar-daily-<plant_id>`, 스케일러는 `serving_app/models/<plant_id>/scaler.pkl`, 업로드는 `data/uploads/<plant_id>/` 다. 지금의 `HAIC_Predictor` 는 전환기 동안 기본 발전소의 이름으로 남길 수 있다.
- 모델, 스케일러, 피처의 뜻은 **묶음 기록**으로 함께 식별한다. 학습할 때 발전소, 모델 이름과 버전, 스케일러의 해시, 피처의 뜻, 학습 자료의 해시와 끝 날짜를 남기고, 불러올 때 요청한 발전소와 스케일러의 해시를 견준다. 어긋나면 불러오지 않는다.
- 응답의 `model_version` 은 레지스트리의 실제 번호다([0008](0008-retraining-and-version-switch.md)). 번호는 발전소마다 따로 간다.

**기존 요청은 (가)로 받는다.** `plant_id` 를 주지 않으면 기본 발전소(`hadong-sewage`)로 본다. 응답에는 필드를 더할 뿐 기존 필드를 바꾸지 않는다. 필수로 바꾸는 시점은 따로 정한다. 포트폴리오의 조회와 예측은 새 경로로 더한다.

**학습과 평가**

- 창은 발전소별로, 날짜가 하루씩 이어지고 값이 있는 구간에서만 만든다. 발전소의 행을 이어 붙이지 않는다. 결측은 0 으로 채우지 않는다.
- 학습, 검증, 시험을 날짜로 나눈다. 포트폴리오의 모든 발전소가 같은 날짜에서 나뉜다. 스케일러는 발전소마다 학습 구간의 행으로만 맞춘다.
- 게이트는 발전소마다 [0005](0005-deployment-gate.md)의 기준을 그 발전소의 기준 예측으로 본다. 한 곳이 실패하면 그 발전소의 이전 버전만 유지한다.
- 합계의 품질은 승격을 막지 않는다. 공통 시험일에서 합계의 RMSE 가 합계에 대한 7일 평균의 80% 이하이고 치우침이 ±10% 이내인지를 계산해 기록하고, 포트폴리오 응답의 "검증됨" 표시에만 쓴다.
- 평가는 발전소별 지표와 포트폴리오 지표를 같은 대상일에서 함께 낸다. 포트폴리오 RMSE 는 예측 합계와 실제 합계로 구한다. 발전소별 RMSE 를 더하지 않는다. 발전소 평균과 발전량 가중을 함께 싣고 커버리지를 붙인다. 단순 기준 예측(전일값, 7일 평균)과 같은 날짜에서 견준다.
- 구성원 가운데 자료나 예측이 없는 곳이 있으면 합계를 내지 않고 누락을 알린다. 구성이 바뀐 앞뒤는 같은 발전소 집합으로 고정해 견준다.
- 용량 1kW 당 RMSE 는 크기가 다른 발전소를 견주는 값이다. 제도의 오차율과 나란히 놓지 않는다([0003](0003-capacity-and-error-metrics.md)).

## 다시 볼 조건

- 발전소가 많아져 학습 시간이나 메모리가 한 PC 의 한도에 닿을 때. 공통 모델을 다시 본다
- 자료가 짧은 새 발전소를 서빙에 올려야 할 때. 게이트를 볼 수 없는 발전소를 어떻게 다룰지 정한다
- 이웃 발전소의 모델을 실제로 학습해 발전소별과 합계의 값을 얻었을 때. 합계의 "검증됨" 기준(80%, ±10%)이 맞는지 본다
- `plant_id` 를 필수로 바꾸기로 할 때
