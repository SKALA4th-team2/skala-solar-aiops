# 여러 발전소 준비의 검증 기록

[`multi-plant-extension.md`](../../multi-plant-extension.md), [`multi-plant-data-contract.md`](../../multi-plant-data-contract.md), [`single-pc-operation.md`](../../single-pc-operation.md)와 결정 기록 0010 ~ 0012 가 "직접 확인했다"고 적은 내용의 기록이다. 문서의 `M` 번호가 여기를 가리킨다. 기획서 ①~⑥ 의 검증 기록(`V` 번호)은 [`../validation.md`](../validation.md)에 따로 있다.

## 읽는 법

- **판정**은 세 가지다. **통과**는 기대와 실제가 같다는 뜻이다. **실패**는 기대한 결과가 나오지 않았다는 뜻이다. **미실행**은 돌리지 못했다는 뜻이고 까닭을 적었다.
- 이 기록은 **준비 도구와 자료**를 검증한 것이다. 여러 발전소를 다루는 서비스는 아직 구현되지 않았으므로 그 동작은 모두 미실행이다([M11](#m11)).
- **합성 자료의 수치는 도구의 기능을 확인하는 데만 쓴다.** 실제 예측 성능이나 제도 요건의 근거가 아니다.
- 실제 자료로 얻은 값은 **단순 기준 예측**(전일값, 7일 평균)의 값이다. 우리 모델의 값이 아니다.

### M02

**합성 자료로 본 실패 사례**

| 항목 | 내용 |
| --- | --- |
| 대상 | 검증·용량·기간·평가·묶음 확인 도구가 잘못된 자료를 실제로 잡는가 |
| 명령 | `python tools/multi_plant/selftest.py --out docs/proposal/evidence/multi-plant` |
| 입력 | 도구가 임시 폴더에 만드는 합성 자료. 발전소 3곳(100, 50, 250kW) × 400일. 정해진 식으로 만들어 돌릴 때마다 같다 |
| 기대 | 21건 모두 기대한 오류나 결과가 나온다 |
| 실제 | 21건 가운데 통과 21건, 실패 0건 |
| 판정 | 통과 |
| 기록 | [`selftest.txt`](selftest.txt), [`selftest.json`](selftest.json) |

| 번호 | 확인한 것 | 결과 |
| --- | --- | --- |
| S01 | 한국남부발전 형식 원자료의 변환(CP949, `(kw)` 가 없는 머리 줄) | 빈 칸은 `partial`, 빠진 날은 `missing` 행, 0 인 날은 `zero_day`, 합계가 다른 날은 `mismatch`. 0 으로 채우지 않는다 |
| S02 | 정상 자료 | 오류 0건 |
| S03 | 같은 발전소의 중복 등록 | 검증이 막는다. 용량 합계는 400kW(중복을 더한 500kW 가 아니다) |
| S04 | kW 와 MW 를 바꿔 적은 용량 | 100kW 를 100MW 로 적으면 "용량에 한참 못 미침", 0.1MW 를 0.1kW 로 적으면 "용량 초과"로 잡는다. 0.1MW 는 100kW 로 통과 |
| S05 | 단위 환산 | 0.055MW = 55kW, 1.2MWh = 1,200kWh, 1,500Wh = 1.5kWh |
| S06 | 빠진 날짜 | 막는다 |
| S07 | 중복 날짜 | 막는다 |
| S08 | 결측 | 빈 값을 `ok` 로 적으면 막는다. `missing` 으로 적으면 받고, 그날이 낀 창 21개를 만들지 않는다 |
| S09 | 음수, `nan`, `inf` | 막는다 |
| S10 | 다른 발전소의 행이 섞인 파일 | 막는다 |
| S11 | 발전소가 섞인 창 | 발전소별로 만든 창 1,140개에 문제 0개. 행을 이어 붙이면 지금의 `build_sequences` 가 오류 없이 섞인 창 40개를 만든다 |
| S12 | 포트폴리오 구성 변경 | 날짜에 따라 구성 버전과 용량 합계가 달라진다(150kW → 400kW). 변경을 걸친 기간의 평가는 멈추고, 발전소를 고정하면 평가한다 |
| S13 | 구성의 오류 | 버전의 기간 겹침, 한 발전소의 이중 소속, 등록부에 없는 발전소를 막는다 |
| S14 | 용량 변경 | 유효 기간으로 그 날의 용량을 고른다(100kW → 120kW). 기간이 겹치면 막는다 |
| S15 | 용량을 모르는 발전소 | 합계에서 빼고 "전체가 아니다"를 알린다 |
| S16 | 일부 발전소의 자료 누락 | 합계를 평가하지 않는다. 자료가 늦게 시작하면 공통 기간이 그만큼 준다 |
| S17 | 일부 발전소의 예측 누락 | 모델의 합계 지표를 내지 않고 누락을 알린다. 일부 날짜만 없으면 모든 방법을 같은 날짜로 좁힌다 |
| S18 | 발전소 A 의 업로드가 B 의 학습에 쓰이는 문제 | 지금의 `latest_upload()` 는 B 의 파일을 고른다(문제의 재현). 발전소별 폴더에서 고르면 A 의 파일을 고른다 |
| S19 | 모델과 스케일러의 짝 불일치 | 같은 출력 0.5 가 253.4kWh 와 623.9kWh 로 되돌려지는데 오류가 없다. 묶음 기록의 해시와 `plant_id` 로 잡는다 |
| S20 | 포트폴리오 RMSE 와 발전소별 RMSE 의 합 | 발전소마다 80kWh 씩 틀려도 합계의 RMSE 는 0 일 수 있다. 일반 합성 자료에서도 포트폴리오 RMSE 239.9kWh 가 발전소별 합 364.3kWh 보다 작다 |
| S21 | 시간대별 자료 | 일부만 있는 날을 하루 값으로 쓰면 막는다. 24칸의 합이 하루 값과 다르면 막는다 |

| 방법 | 시간대마다 "예측과 실제의 차이의 절댓값 ÷ 등록부의 설비 용량 × 100"을 구해, 실제가 용량의 10% 이상인 시간대에서 평균했다. 예측은 어제 같은 시각의 값과 직전 7일 같은 시각의 평균이다. 합계는 구성원의 예측과 실제를 시간대별로 더해 용량 합계로 나눴다. 정지일을 건너뛰지 않았다 |
| 명령 | [M05](#m05)와 같다(`--hourly`) |
| 기대 | 하수처리장 한 곳의 값이 기존 조사의 "정지일 처리 없음" 조건 값(13.84%, 12.20%)과 같다. 5곳의 값이 정지일을 건너뛴 기존 조사의 값(10.98%, 9.60%)과 가깝다 |
| 실제 | 882일(2023-10-01 ~ 2026-02-28): 하수처리장 13.84%, 12.20%. 5곳의 합계 10.97%, 9.72%(대상 6,791시간). 264일(2025-06-09 ~ 2026-02-27): 하수처리장 13.34%, 11.18%. 5곳의 합계 10.50%, 8.98% |
| 판정 | 통과. 한 곳은 같고, 5곳은 0.12%p 안에서 같다(정지일 처리의 차이) |
| 기록 | [`real5_evaluate.txt`](real5_evaluate.txt). 기존 조사의 값은 [`out_01_capacity_sens.txt`](../../../research/merged/files/T7-value/out_01_capacity_sens.txt)의 2b, 3b 절 |

**이 값은 정산 성능이 아니다.** 학습이 없는 기준 예측이고 우리 모델의 값이 아니다. 606.17kW 는 20MW 묶음이 아니다. 분모가 제도의 유효 설비 용량이 아니라 공시 설치용량이다. 전날 10시와 17시에는 받을 수 없는 전날 저녁까지의 값을 썼다.

### M09

**한 PC 측정**

| 항목 | 내용 |
| --- | --- |
| 대상 | 발전소 한 곳의 학습 시간과 메모리, 메모리의 모델 하나가 차지하는 크기, 학습 중의 예측 시간, 두 프로세스의 동시 기록 |
| 명령 | `python tools/multi_plant/single_pc_probe.py --project <사본 폴더>/project --out <임시 폴더>`, 이어서 `--steps finetune` |
| 입력 | 커밋 `9ad93b1` 의 `project/` 를 푼 사본에 `datasets/hadong_upload_forecast_jma.csv`(1,337행)를 넣은 것 |
| 기대 | 모든 단계가 끝난다. 학습 중에도 예측이 실패하지 않는다 |
| 실제 | 처음 학습 18.0초(최대 메모리 581MB). MLflow 학습 22.0초(696MB, 디스크 1.07MB 증가, 지금의 게이트 4.00 에서 막힘: RMSE 41.59). 재학습 4.36, 4.35, 4.46초. 프로세스 메모리는 TensorFlow 를 올린 뒤 489MB, 모델 1개 518MB, 8개 550MB(모델 하나마다 4.6MB). 예측 한 건의 계산 시간의 중앙값과 95번째 백분위는 한가할 때 12.9ms, 13.7ms(200건), 다른 프로세스가 학습할 때 14.4ms, 16.1ms(1,540건), 같은 프로세스의 다른 스레드가 학습할 때 15.3ms, 21.9ms(1,299건). 예측 실패 0건. 두 프로세스가 같은 `mlflow.db` 에 30건씩 쓴 60건이 모두 성공(1.5초) |
| 판정 | 통과 |
| 기록 | [`single_pc_probe.json`](single_pc_probe.json) |

- 예측 시간은 HTTP 를 거치지 않은 모델 계산 시간이다. 엔드포인트의 응답 시간이 아니다.
- 재학습 시간은 측정 프로세스 안에서만 게이트를 열고 쟀다. 코드의 게이트 값은 그대로이고, 그 통과는 품질의 근거가 아니다.
- 발전소 한 곳, 조사에 쓴 PC 의 값이다. 여러 발전소의 값은 [한 PC 운영 문서 4절](../../single-pc-operation.md#4-규모-산정식)의 식으로 어림한 추정이다.

### M11

**돌리지 못한 것**

| 무엇 | 왜 | 언제 |
| --- | --- | --- |
| 여러 발전소의 업로드, 학습, 서빙, 감시, 재학습의 실제 동작 | 서비스가 아직 발전소 한 곳만 다룬다. 이번 범위는 준비다 | [확장 문서 9절](../../multi-plant-extension.md#9-다음-구현-작업)의 순서대로 구현한 뒤 |
| 이웃 4곳의 모델 학습과, 모델로 본 발전소별·합계의 오차 | 발전소별 예보 입력이 없다. 보건소는 공시된 좌표가 없다 | 발전소별 예보를 받은 뒤 |
| 다른 지역 발전소의 자료 | 자료가 아직 없다. 백엔드를 돌릴 PC 에 둘 예정이다 | 자료가 들어온 뒤 [자료 계약 6절](../../multi-plant-data-contract.md#6-새-자료를-넣는-절차)대로 |
| 백엔드를 돌릴 PC 에서의 측정 | 그 PC 가 아니다 | 그 PC 에서 `single_pc_probe.py` 를 돌린다 |
| 컨테이너에서의 동작과 측정, 볼륨을 건 뒤의 복구 | 컨테이너를 만들지 않았다 | 컨테이너 작업 때 |
| 재학습 중의 엔드포인트 응답 시간, 작업 기록과 일꾼의 동작 | 설계만 했다 | [0012](../../../decisions/0012-single-pc-retrain-jobs.md)를 구현한 뒤 |
| 제도 기준의 정산용 묶음 오차율 | 발전기별 시간대별 예측 모델, 유효 설비 용량, 20MW 초과의 실제 묶음이 없다 | 범위 밖이다([0010](../../../decisions/0010-multi-plant-scope-and-scheme.md)) |
| 구성이 바뀐 앞뒤의 실제 비교 | 실제 구성의 이력이 없다. 기능만 합성 자료로 확인했다(S12) | 실제 구성이 생긴 뒤 |
| 부하 시험 | 하지 않았다 | 구현한 뒤. 복제한 자료는 부하 시험에만 쓴다 |
