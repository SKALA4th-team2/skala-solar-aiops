# ③ 운영 설계

## 통합가이드가 요구하는 것

스키마·성능 회귀·임계값을 포함한 배포 게이트, 모니터링 지표, 알림→재학습→재검증→유지·롤백 정책을 근거와 함께 설계한다. 모든 수치는 [결정0014](../decisions/0014-hourly-forecast-and-aiops.md)와 같은 코드에 반영했다.

## 최초 배포 게이트

- 유효 평가일180일 이상.
- RMSE≤전날 같은 시간 유지 RMSE×0.95.
- RMSE≤훈련 기간 일사량 기준선 RMSE×1.05.
- 발전량 합계 편향 절댓값≤15%.
- 주간 RMSE≤일사량 기준선 주간 RMSE×1.05.

야간이 포함된 전체 오차와 주간 오차를 함께 본다. 임계값은 교육용 운영 정책이며 정산 기준이 아니다. 33개소 실행 전에 고정했고 실패 개소를 통과시키기 위해 완화하지 않았다. 시간별 품질 미달 신인천전망대·용수리는 운영에서 제외했다.

## 시간별 모니터링과 대응

| 조건 | 판정·동작 |
| --- | --- |
| 불완전한 시간,중복,음수,비유한값,용량 초과 | 요청 거절; 결측을0으로 대체하지 않음 |
| 최근7일 미충족 또는 일사량≥20W/m²인 주간48시간 미충족 | 자료 부족으로 검사 생략 |
| 일사량≥150W/m²·실적≤기준선10% 구간이3시간 연속 | 데이터·설비 점검 보류; 자동 재학습하지 않음 |
| 실적합/예보 일사량 기준선합<0.85이고 RMSE>최초 한도 | 드리프트 후보; 추가 자격 검사 후 큐 등록 |
| 새 학습 대상이 기존 훈련 기간과 겹침 또는696시간 미충족 | 재학습 보류 |
| 나머지 | 정상; 모델 유지 |

이 기준선은 예보에 조건을 둔 잔차 검사다. 현장 관측기상으로 보정한 PI나 고장 확정 진단은 아니다. 경고·후보·작업·배포 결과는 events 테이블과 aiops-hourly.log로 남기고 프론트에서 조회한다.

## 재학습·등록·복구

연속29일696시간에서 첫날은lag24,다음21일은학습,마지막7일은검증이다. 기존 모델을5epoch 추가 학습하고 scaler는 다시 맞추지 않는다. 후보 RMSE가 최초 한도와 동일 검증창 기존 모델 RMSE 이하일 때만 운영으로 승격한다. 후보와 검증 결과는 MLflow에 기록한다. 실패 시 기존 모델을 유지한다.

단일 작업자와 OS 잠금이 중복 실행을 막는다. 같은 개소·종료시각 작업은 중복 등록하지 않고 다른 입력 해시는 충돌로 거절한다. 중단 작업은 최대2회 시도하며, 레지스트리와 current.json을 재조정한다. 교체 전 모델·스케일러 SHA 및 입력/출력 모양을 확인한다. 손상 모델 로드가 실패하면 이미 적재된 정상 모델을 유지하고, 초기 로드부터 실패하면503을 반환한다.

성공 단건 예측과 배치 예측은 입력·출력·모델 버전·입력 해시·기록 시각을 predictions 테이블에 저장한다. API 재시작 뒤에도 조회할 수 있다. 과거 재생을 운영 당시 예측 기록으로 혼동하지 않도록 kind를 forecast와retrospective_batch로 구분한다.

## 정책 근거와 측정 방법

아래 값은 실험으로 최적화된 상수나 제도 요건이 아니라 시간별 서비스의 교육용 정책이다. 민감도 분석과 장기 운영 검증은 아직 수행하지 않았다.

| 정책/목표 | 선택 이유 | 측정·판정 방법 |
| --- | --- | --- |
| 최소 평가 180일 | 짧은 유리한 기간만으로 승인하지 않기 위한 최소 범위 | 2025년 연속 전날 입력을 확보한 유효 평가일 수 |
| lag24 대비 RMSE 5% 개선 | 단순 전날 유지보다 개선을 요구 | 동일 시간의 테스트 RMSE 비교 |
| 일사량 기준 대비 5% 허용, 편향 15% | 물리적 기준보다 크게 나빠지거나 한쪽으로 치우친 모델 제외 | 전체·일사량≥20 주간 RMSE, 100×오차합/실적합 |
| 최근 7일·주간 48시간 | 단일 시간 잡음과 야간 0값의 영향 억제 | inspect의 일 단위 창과 주간 마스크 |
| 기준 실적 비율 0.85와 RMSE 동시 초과 | 낮은 발전량만으로 재학습하지 않기 위한 두 조건 | 예보 기반 기대량 합 대비 실제 합, 최초 RMSE 한도 |
| 3시간 연속 주간 극저발전 보류 | 설비/자료 이상을 학습하는 것을 피함 | 일사량≥150, 실제≤기준10% 연속 검사 |
| 21일 학습·7일 검증 | 최근 변화 반영과 시간순 검증 분리 | 696시간에서 24시간 입력 준비 후 504/168시간 분할 |
| API 지연·오류율 | 요청 처리를 측정하는 서비스 목표 | HTTP middleware의 ms·상태코드; 재시작 시 메모리 지표 초기화 |
| 작업자 동작·복구 | 작업 멈춤과 예측 이력 손실 감시 | heartbeat 120초, Docker 재시작 후 저장 응답 동일성 |
| 모델 변경 안정성 | 검증 실패 시 성능 후퇴 방지 | 같은 검증창 기존 모델과 비교, 이전 버전 복원 예측 대조 |

장기 가용성 99% 등의 목표 달성을 단기 기능 테스트로 주장하지 않는다. 같은 종료시각의 기존 작업은 queued/running/succeeded/rejected/failed 상태를 그대로 반환하며, 완료 작업 재조회는 재실행이 아니다. 후보는 게이트 실패 결과도 MLflow에 등록할 수 있지만 운영 승격은 통과한 경우만 수행한다.
