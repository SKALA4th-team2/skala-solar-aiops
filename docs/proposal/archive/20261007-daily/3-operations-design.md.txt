> **2026-10-07 시간별 전환 — 현행:** 최근7일168시간·주간48시간 이상, 예보 기준선 실적비<0.85와 최초 RMSE 한도 초과 시 후보. 주간3시간 연속 극저발전은 보류. 29일 데이터로21일학습/7일검증,5epoch, scaler고정. 최초한도·동일창기존모델을 모두 통과해야 승격. [운영 안내](../backend-runbook.md) · [결정0014](../decisions/0014-hourly-forecast-and-aiops.md). 이하 이전 계약·수치는 설계/검증 이력이며 현행 시간별 계약보다 우선하지 않는다.

# ③ 운영 설계

> **2026-10-07 구현 갱신:** 최초 게이트는 180일 이상, Mean7 RMSE의 80% 및 RuleC의 105% 이하, 편향 ±10%다. 고정 PI 기준선 대비 21일/유효 15일·−7.5% 저하와 앞 20일의 저하를 함께 본다. 최근 41행의 정지·보류는 재학습을 막는다. 재학습은 16표본 학습/5표본 검증, 기존 모델보다 나쁘지 않고 최초 kWh 한계 이하여야 승격한다. RMSE 1.5배는 보조 경고다. [채택 정책](../decisions/0013-backend-aiops-implementation.md)과 [실행 안내](../backend-runbook.md)가 현재 구현 기준이다. 아래 기존 제안·과거 측정은 이력으로 보존한다. 프론트는 이번 범위에서 제외했다.

- 평가 항목: 2-1 (설계)
- 담당:
- 상태: 초안 (2026-10-07). 이 문서의 정책과 숫자는 모두 상태가 "제안"인 결정 기록을 따른다. 팀이 확정한 값은 아직 없다. 발전소가 여럿일 때 대상별로 달라지는 정책은 [14절](#14-여러-발전소일-때의-게이트-감시-재학습-확장-제안)에 따로 적었다

### 2. 입력 검증

틀린 입력을 예측 전에 거른다. 두 곳에서 한다. 예측 요청이 들어올 때와 학습 자료를 올릴 때다.

**예측 요청 (`POST /predict`)**

| 무엇을 보는가 | 지금 | 실행해 본 결과 | 제안 |
| --- | --- | --- | --- |
| 길이 | 정확히 20개 | **[실행]** 19개와 21개 모두 422 | 그대로 |
| 첫째 값의 타입과 범위 | 실수, 0 초과 | **[실행]** 0 은 422. 발전량이 0 인 날을 넣을 수 없다 | 실수, 0 이상 1,320 이하(kWh) |
| 둘째 값의 타입과 범위 | 정수, 0 이상 | **[실행]** 소수는 422, 음수는 422. 예보 값(소수)을 넣을 수 없다 | 실수, 0 이상 45 이하(MJ/m²) |

- **[제안]** 범위는 정상 값을 거르려는 것이 아니다. 원본의 하루 발전량은 0 ~ 379.8kWh, 예보는 0.95 ~ 28.4MJ/m² 다. 1,320(55kW × 24시간)과 45(대기권 밖 일사량의 연중 최댓값 41.5 보다 조금 큰 값)는 단위를 잘못 넣은 값을 거르는 선이다. ([V18](evidence/validation.md#v18))

**업로드 파일 (`POST /data/upload`)**

### 3. 학습과 평가를 나누는 방법과 스케일러

| 항목 | 지금 | 제안 |
| --- | --- | --- |
| 나누는 방법 | 시간순으로 앞 80% 가 학습, 뒤 20% 가 평가다(`data/features.py` 의 `train_test_split`). 섞지 않는다 | 그대로 |
| 지금 파일에서의 구간 | **[실행]** 학습 정답일 2022-07-22 ~ 2025-06-08(1,053건), 평가 정답일 2025-06-09 ~ 2026-02-27(264건) | 평가 구간이 180일보다 짧으면 게이트를 판정하지 않는다 |
| 스케일러를 맞추는 구간 | 파일 전체(`scripts/train_baseline_v1.py` 68행). 평가 구간의 최소·최대를 미리 본다 | 학습 행만으로 맞춘다 |
| 스케일러를 쓰는 곳 | MLflow 학습, 재학습, 서빙이 같은 파일(`serving_app/models/scaler.pkl`)을 읽는다 | 그대로 |
| 재학습 때 | 다시 맞추지 않는다 | 그대로. 가중치가 그 기준으로 학습돼 있다 |
| 파일 종류를 바꿀 때 | 규칙만 있다([`AGENTS.md`](../../AGENTS.md)) | 스케일러와 모델을 함께 다시 만든다 |

- **[실행]** 이 파일에서는 스케일러를 학습 행만으로 맞춰도 최소·최대가 같다. 그래서 [② 의 7절](2-solution-and-goals.md#7-단순한-기준-예측과-견주면)의 오차에는 영향이 없었다. 다른 파일에서는 달라질 수 있다. ([V18](evidence/validation.md#v18))
- **[실행]** 스케일러와 모델이 어긋나는 일이 검증 중에 실제로 생겼다. HAIC 예시 파일로 버전 1 을 올린 뒤 태양광 파일로 baseline 스크립트를 돌리자, 스크립트는 빈칸에서 멈췄지만 스케일러는 그 앞에서 이미 태양광 값(5.886 ~ 338.832)으로 덮어썼다. Production 은 주가로 학습한 버전 1 그대로였다. ([V10](evidence/validation.md#v10))
- **[제안]** 스케일러는 모델 버전과 짝이 지어져 있지 않다. 발표까지는 절차로 막는다. baseline 스크립트는 파일 종류를 바꿀 때만 돌리고, 그때는 모델을 반드시 새로 올린 뒤에 서빙한다. **[과제]** 그 뒤에는 스케일러를 모델과 함께 MLflow 에 기록해 버전과 짝을 짓는다([0008](../decisions/0008-retraining-and-version-switch.md)).

### 4. 배포 게이트

새로 학습한 모델을 운영으로 올릴지 정하는 합격선이다.

**[제안]** 처음 학습한 모델은 세 조건을 모두 채워야 올린다([0005](../decisions/0005-deployment-gate.md)).

| 조건 | 기준 | 무엇을 거르는가 |
| --- | --- | --- |
| 1 | 시험 구간의 RMSE ≤ 같은 날짜의 7일 평균 RMSE × 0.80 | 예보를 쓰지 못하는 망가진 모델 |
| 2 | 시험 구간의 RMSE ≤ 같은 날짜의 규칙C RMSE × 1.05 | 학습이 필요 없는 규칙보다 뚜렷하게 나쁜 모델 |
| 3 | 시험 구간의 치우침이 ±10% 이내. ±5% 를 넘으면 올리되 경고 | 한쪽으로 치우친 모델. RMSE 만으로는 걸러지지 않는다 |

- 평가 구간: 시간순으로 나눈 뒤 20%. 180일 이상이어야 한다.
- 기준 모델: 7일 평균(직전 7일의 발전량 평균)과 규칙C((직전 7일의 발전량 합 ÷ 그 7일에 대한 예보의 합) × 대상일의 예보). 둘 다 학습이 없고 창 안의 값만으로 계산된다.
- 통과: MLflow 에 새 버전으로 등록하고 Production 으로 올린다.
- 실패: 등록하지 않는다. 운영 버전은 그대로다. 실패를 `aiops.log` 에 남긴다.

지금의 자료에서 이 기준이 어떤 값이 되는지 계산했다.

| 값 | 결과 | 성격 |
| --- | --- | --- |
| 합격선 | 7일 평균 71.65 × 0.80 = 57.32kWh, 규칙C 45.26 × 1.05 = 47.53kWh(반올림하기 전의 45.2626 으로 계산했다). 둘 다 채우려면 **47.53kWh 이하** | **[실행]** 시험 264일. ([V19](evidence/validation.md#v19)) |
| 직접 학습한 모델 | RMSE 41.59kWh, 치우침 −6.0%. 조건 1 과 2 를 채우고, 3 은 ±10% 안이지만 ±5% 를 넘어 경고 대상이다 | **[실행]** 시드 42 한 번. ([V30](evidence/validation.md#v30)) |
| 지금의 코드로 같은 모델을 학습하면 | `[GATE FAILED] rmse=41.59 > 4.0 -> 배포 차단, 기존 Production 유지` | **[실행]** 4.00 은 주가의 눈금이다. 이 구간의 하루 평균 발전량(194kWh)의 2% 다. 직접 학습한 모델도 기준 예측 넷도 열 배 넘게 벗어나 있어 통과할 모델을 기대할 수 없다. ([V12](evidence/validation.md#v12)) |
| 실패한 뒤의 레지스트리 | 새 버전이 생기지 않았고 버전 1 이 Production 으로 남았다 | **[실행]** "실패하면 기존 버전 유지"가 레지스트리 수준에서 확인됐다. ([V12](evidence/validation.md#v12)) |

![같은 264일에서 견준 다음 날 발전량 예측 오차](assets/quality_test264.png)

발전 실적: 한국남부발전(공공데이터포털). 일사량 예보: [Weather data by Open-Meteo.com](https://open-meteo.com/).

절댓값(예: 47.5kWh 이하)으로 적지 않고 기준 예측과 견주는 까닭은 계절이다. **[조사]** 봄이 들어간 구간은 기준 예측의 오차부터 커진다(공통 구간의 3 ~ 5월에 7일 평균 RMSE 102.7kWh. [T4](../research/merged/T4-performance-gate.md)). 절댓값은 평가 구간이 바뀌면 뜻이 달라진다.

이 기준의 한계는 다음과 같다.

- **[조사]** 80% 와 105% 는 같은 평가 구간에서 정하고 센 값이다. 예보 자료가 2022-07 이후에만 있어 다른 해로 검증하지 못했다.
- 시험 구간에 3 ~ 5월이 없다.
- **[실행]** 달로 나누면 아홉 달 가운데 석 달은 모델이 규칙C 보다 나쁘다(2025-11, 2025-12, 2026-01). 통과가 "모든 달에 규칙보다 낫다"는 뜻이 아니다. ([V30](evidence/validation.md#v30))
- 지금의 통과 계산을 운영 품질의 보증으로 쓰지 않는다.

### 5. 감시: 무엇을, 얼마나 모아, 어디서 선을 긋는가

**[제안]** 올린 뒤에는 예측의 오차가 아니라 **발전소의 출력 수준**을 지켜본다([0006](../decisions/0006-monitoring-metric-and-thresholds.md)).

| 항목 | 값 | 설명 |
| --- | --- | --- |
| 지표 | 성능 지표의 편차 | 성능 지표는 유효한 날의 실제 발전량 합 ÷ 기대 발전량 합이다. 실제 발전량은 하루씩 기대의 0.5 ~ 1.5배로 자른다. 기대 발전량은 그날의 관측 날씨로 계산한다 |
| 기준선 | 모델을 올린 날까지의 365일로 계산해 고정 | 새 모델을 올릴 때와 사람이 수준 변화를 확인했을 때 다시 계산한다 |
| 주기 | 하루에 한 번. 관측 날씨가 공개된 뒤 가장 최근 41일을 배치로 보낸다 | 지금은 사람이 배치를 보낼 때만 판정한다. 날마다 자동으로 돌리는 것은 구현 과제다 |
| 창 | 배치의 뒤 21일(판정 구간). 앞 20일은 예측의 입력이다 | `WINDOW_SIZE = 21` 을 그대로 쓴다 |
| 최소 표본 | 유효한 날 15일 이상 | 모자라면 판정하지 않는다 |
| 임계값 | 편차가 −7.5% 아래 | 내려가는 쪽만 본다 |
| 보조 지표 | 21건 RMSE 가 게이트 때 기록한 시험 RMSE 의 1.5배 초과 | "입력 이상 의심"만 알린다. 재학습하지 않는다. 직접 학습한 모델이면 62.4kWh |

- 성능 지표는 대상일의 관측 날씨가 있어야 계산된다. **예측 시점에는 받을 수 없고 지난 뒤의 감시에만 쓴다.** 그날까지의 판정은 관측이 공개되는 다음 날에 나온다.
- **[현재]** 지금의 코드는 최근 21건의 RMSE 가 4.00 을 넘으면 드리프트로 본다(`drift_detector.py` 22 ~ 23행). 빈칸 때문에 돌지 않는다.

왜 RMSE 가 아니라 성능 지표인가. 같은 배치 둘을 두 지표로 재 보았다.

| 배치 (대상 2025-07-11 ~ 07-31) | 21건 RMSE | 성능 지표의 편차 |
| --- | --- | --- |
| 변화 없음 | 45.1kWh | −2.2% |
| 발전량에 0.86 을 곱함(14% 하락) | 34.5kWh | −15.6% |

- **[실행]** RMSE 는 직접 학습한 모델(시드 42)의 값이다. 수준이 14% 내려갔는데 RMSE 는 오히려 내려갔다. 이 모델이 원래 낮게 예측하고 있었기 때문이다(치우침 −8.7% 에서 +2.2% 로). 지금 코드의 기준 4.00 에 견주면 두 배치 모두 넘는다. 눈금을 고치지 않으면 배치를 보낼 때마다 재학습이 걸린다. ([V30](evidence/validation.md#v30))
- **[실행]** 성능 지표의 편차는 기준선(2025-02-28 까지 365일, 0.951)에 견준 값이다. 두 배치가 임계값의 양쪽으로 갈린다. ([V21](evidence/validation.md#v21))
- **[조사]** 조사에서도 같았다. 예보를 넣은 실습 LSTM 에서 14% 하락을 넣은 배치와 넣지 않은 배치가 "학습 RMSE 의 1.3배"라는 기준을 넘는 비율이 13.2% 와 14.0% 였다. 학습이 2025-02-28 에서 끝나는 다른 모델의 저장된 결과다([T5](../research/merged/T5-drift-demo.md)).

실제 사건에서도 갈린다.

![21일 배치의 성능 지표가 기준선에서 벗어난 정도](assets/pi_deviation_scenes.png)

발전 실적: 한국남부발전(공공데이터포털). 날씨 관측: 기상청 종관기상관측(ASOS) 광양(266).

- **[실행]** 2021년: 기준선 0.9809. 하락 전 배치 −0.8%, 하락 뒤 배치 −14.6%. ([V20](evidence/validation.md#v20))
- 2021년의 두 막대는 실제 사건의 사후 분석이다. 2025년의 두 막대 가운데 아래 것(× 0.86)만 인위로 낮춘 값이고, 위의 것은 같은 날짜의 실제 값이다. 날짜는 조사에서 결과를 보고 골랐다. 독립된 성능 평가가 아니다.

### 6. 임계값을 낮추거나 높이면

![한도를 바꾸면 오경보와 놓침이 함께 움직인다](assets/threshold_tradeoff.png)

발전 실적: 한국남부발전(공공데이터포털). 날씨 관측: 기상청 종관기상관측(ASOS) 광양(266).

**[실행]** 기준선을 2025-02-28 에 고정하고, 2025-03-08 ~ 11-15 의 7일 간격 시작일 37개에서 판정했다. 칸의 값은 임계값을 넘은 배치의 수다. ([V22](evidence/validation.md#v22))

| 임계값 | 변화가 없는 배치 (넘으면 오경보) | 8.5% 낮춘 배치 (못 넘으면 놓침) | 14% 낮춘 배치 (못 넘으면 놓침) |
| --- | --- | --- | --- |
| −5% | 7개 (18.9%) | 28개 (75.7%) | 37개 (100%) |
| **−7.5%** | **1개 (2.7%)** | **25개 (67.6%)** | **34개 (91.9%)** |
| −10% | 0개 | 20개 (54.1%) | 29개 (78.4%) |
| −12.5% | 0개 | 10개 (27.0%) | 25개 (67.6%) |

- −5% 로 내리면 변화가 없는데도 다섯 번에 한 번 꼴로 켜진다. 알림을 믿지 않게 된다.
- −10% 로 올리면 2021년에 실제로 본 크기(앞뒤 1년 8.5%)의 하락을 절반 가까이 놓친다.
- −7.5% 는 그 사이다. 14% 하락은 열에 아홉, 8.5% 하락은 셋에 둘을 잡는다. 나머지는 놓친다.
- 크게 떨어지면 다른 길로 간다. 20% 를 낮추면 37개 가운데 10개가, 30% 를 낮추면 35개가 유효한 날이 모자라 판정되지 않는다. 정지와 보류로 빠지기 때문이다(7절).

위의 표는 내려간 뒤의 날로 21일이 모두 찬 배치를 센 것이다. 그런 배치는 내려간 날로부터 41일 뒤에야 만들어진다. 알림까지의 시간을 보려면 날마다 판정했을 때를 따로 세어야 한다.

**[실행]** 날마다 그날까지의 21일로 판정한다고 하고, 내려간 날을 1일째로 세어 처음 임계값(−7.5%)을 넘는 날을 찾았다. 변화가 없어도 봄의 한 구간(2025-04-14 ~ 04-20, 7일)에서 임계값을 넘으므로, 그 구간을 만나는 앞의 시작일 7개를 빼고 30개(2025-04-26 ~ 11-15)로 셌다. ([V22](evidence/validation.md#v22))

| 낮춘 크기 | 21일 안에 넘음 | 28일 안에 넘음 | 41일 안에 넘음 | 넘은 날의 가운데 값 |
| --- | --- | --- | --- | --- |
| 14% | 27개 | 28개 | 30개 | 8일째 |
| 8.5% | 22개 | 23개 | 23개 | 11일째 |

- 14% 를 낮춘 경우는 대부분 한두 주 안에 넘는다. "4주 안에 알린다"는 [② 의 목표](2-solution-and-goals.md#6-운영-목표)가 이 크기에서는 30개 가운데 28개로 채워진다.
- 8.5% 를 낮춘 경우는 23개만 넘고 7개는 41일이 지나도 넘지 못한다. 그 7개는 모두 10 ~ 11월에 시작한 것이다. 이때는 변화가 없어도 성능 지표가 기준선보다 높게 나와, 8.5% 가 내려가도 임계값에 닿지 않는다.
- 관측 날씨가 하루 늦게 공개되므로 실제로 알게 되는 날은 하루 뒤다.
- 변화가 없는 2025-03-08 ~ 12-31 의 299일을 날마다 판정하면 임계값 아래인 날이 7일(2025-04-14 ~ 04-20), 한 번의 구간이다. 알려진 변화가 없는 때의 경고이므로 오경보로 센다.
- 이것도 인위로 낮춘 값으로 한 표본 안의 계산이다. 서버의 판정으로 확인한 것이 아니다.

이 표의 한계는 다음과 같다.

- 임계값과 날짜를 같은 자료에서 보고 골랐다. 다른 해로 검증한 값이 아니다.
- 배치가 37개뿐이고 서로 겹친다. 한 개가 2.7%p 다. 비율을 확률로 읽으면 안 된다.
- **[실행]** 변화가 없는 배치 37개의 편차가 −8.5% 에서 +9.1% 까지 퍼져 있다(가운데 −2.2%). 가장 낮은 것은 3월에, 가장 높은 것은 10월에 시작한 배치다. 기준선은 한 해의 평균이라 계절을 반영하지 않는다. **[조사]** 조사는 이 흔들림을 계절 탓으로 추정했다([T5](../research/merged/T5-drift-demo.md)). 확인된 원인은 아니다.
- 기준선을 오래 고정하면 낡는다. **[조사]** 2021년의 기준선을 그대로 둔 채 2025-03 ~ 12 를 날마다 감시하면(30일 창, 3일 연속) 하락 경고가 5번, 59일 켜졌다([T5](../research/merged/T5-drift-demo.md)). 그래서 모델을 올릴 때마다 기준선을 다시 계산한다.
- 올라가는 쪽(정비 뒤의 회복)은 잡지 못한다.
- **기대 발전량을 계산하는 관측 자체가 변하면 가짜 경고가 난다.** **[조사]** 광양의 관측 일사량이 이웃 관측소에 견줘 4 ~ 6% 낮아진 것으로 보이는 구간이 있다([T2](../research/merged/T2-history-outage.md)). 가까운 적량면의 관측 자료에서는 센서의 수준이 계단처럼 바뀐 일이 세 번 보였다.

![입력 자료도 변한다: 가까운 관측소(적량면) 일사량 센서의 수준](assets/sensor_ratio.png)

- **[조사]** 이 그림은 [적량면 관측 자료 검토](../research/jeokryang-sensor.md)의 내용이다. 그 문서는 한 사람이 한 분석이고 다른 사람의 재확인을 받지 않았으며 통합 보고서에 들어 있지 않다. 계단이 센서의 교체나 수리 때문인지는 확인되지 않았다. **[미확인]** 이 자료의 출처 기관과 이용 조건도 확인되지 않았다([`../followups.md`](../followups.md) 6, 7번). 감시의 기준으로 쓰는 관측도 변할 수 있다는 점을 보이려고 실었고, 이 자료를 서비스의 입력으로 쓰지는 않는다.

### 7. 설비 이상 후보와 모델 품질 저하를 가른다

**[제안]** 예측이 어긋나는 원인을 둘로 가른다([0007](../decisions/0007-facility-vs-model-branch-and-alerts.md)). x 는 그날의 실제 발전량, e 는 그날의 관측 날씨로 계산한 기대 발전량이다.

| 이름 | 조건 | 처리 |
| --- | --- | --- |
| 정지 | x 가 0 이하이거나, e 가 30kWh 이상인데 x 가 e 의 30% 미만 | 판정과 재학습에서 뺀다 |
| 낮은 날 | 정지이거나, e 가 80kWh 이상인데 x 가 e 의 70% 미만 | 보류를 센다 |
| 보류 | 그날까지의 7일에 낮은 날이 3일 이상 | 판정과 재학습에서 뺀다. 설비 점검을 알린다 |
| 하루 점검 알림 | e 가 80kWh 이상인데 x 가 e 의 50% 미만 | 그날 하루의 알림 |

배치가 들어오면 위에서부터 본다. 흐름 그림은 [④ 의 4절](4-architecture.md#4-수준-저하에-대응하는-갈래)에 있다.

| 순서 | 조건 | 판정 | 할 일 |
| --- | --- | --- | --- |
| 1 | 유효한 날이 15일 미만 | 판정하지 않음. 정지나 보류가 있었으면 **설비 이상 후보** | 설비 담당자에게 점검 알림. **재학습 보류** |
| 2 | 뒤 21일의 성능 지표 편차가 −7.5% 아래 | **출력 수준 저하** | 운영자와 설비 담당자에게 알림 |
| 2-1 | 2번이면서 앞 20일의 편차도 −7.5% 아래 | 41행 전체가 내려간 수준 | 재학습 후보를 만들어 게이트로 보낸다. 앞 20일이 아직 아래가 아니면 알리기만 하고 기다린다 |
| 3 | 21건 RMSE 가 보조 한도 초과 | 입력 이상 의심 | 운영자에게 알림. 재학습 없음 |
| 4 | 그 밖 | 정상 | 없음 |

- 재학습에 쓸 41행 안에 정지나 보류인 날이 있으면 2-1번이어도 재학습을 미룬다. 실습 코드는 그 날만 빼고 학습할 수 없다.
- **[실행]** 규칙을 원본 4,807일에 적용하면 정지 49일, 보류 68일, 유효한 날 4,658일이다. 파일에 들어 있던 유효일 표시와 모두 같았다. ([V20](evidence/validation.md#v20))
- **[실행]** 2025-03-31 은 실제 141.5kWh, 기대 296.2kWh 로 비율이 0.48 이다. 하루 점검 알림의 조건에 든다. 정지와 보류는 아니다. ([V23](evidence/validation.md#v23))
- **[조사]** 2024-07-10 ~ 07-18 의 9일은 실제가 기대의 0.26 ~ 0.64배였고 규칙은 07-12 ~ 07-22 를 보류로 둔다([T5](../research/merged/T5-drift-demo.md)).

출력 수준이 내려갔을 때 원인이 설비일 수 있는데도 재학습 후보를 만드는 까닭은, 예측의 목표가 실제 발전량이기 때문이다. 수준이 내려간 채로 이어지는 동안에는 원인이 무엇이든 예측이 그 수준을 따라야 한다. 다만 재학습이 늘 나아지게 하지는 않으므로 게이트를 거친다.

- **[조사]** 14% 하락을 넣은 실험의 평균에서 재학습 뒤 치우침이 +7.4% 에서 −0.9% 로 줄었다. RMSE 는 37.7kWh 에서 35.8kWh 로 조금 줄었고, 줄어든 시작일은 시드에 따라 46.5 ~ 72.1% 였다. 예보를 넣은 실습 LSTM 이지만 학습이 2025-02-28 에서 끝나는 다른 모델이고, 조사가 저장해 둔 결과를 다시 집계한 값이다. 우리가 학습한 모델로는 재지 않았다. ([T5](../research/merged/T5-drift-demo.md))
- **[조사]** 2021년의 실제 하락에서는 재학습 전후의 RMSE 가 같았다(66.2kWh 대 65.9kWh). 발전량만 넣은 또 다른 모델의 결과이고, 그 입력에는 예측 시점에 받을 수 없는 날씨 값이 한 칸 섞여 있었다. 원 조사의 인용이다. ([T5](../research/merged/T5-drift-demo.md))
- **"재학습하면 정확도가 돌아온다"고 쓰지 않는다.** 쓸 수 있는 말은 "인위로 14% 를 낮춘 실험의 평균에서 치우침이 줄었다"까지다.

이 규칙의 한계는 다음과 같다.

- **[조사]** 한도(30%, 50%, 70%, 30kWh, 80kWh, 7일 가운데 3일)는 전체 기간을 보고 고른 값이다. 정답으로 삼은 달력도 이웃 발전소와 견줘 사후에 만든 것이지 정비 기록이 아니다.
- "설비 이상 후보"는 진단이 아니다. 무엇이 고장 났는지는 말하지 못한다.
- 관측 날씨를 받지 못하는 날에는 이 규칙을 쓸 수 없다.

### 8. 알림

| 상황 | 알릴 사람 | 로그의 문장 |

| 재학습 시작 | 서비스 운영자 | `[INFO] retrain triggered (window=last_21_days)` |

| 게이트 실패 | 서비스 운영자 | `[WARN] gate failed - production kept (new_rmse=..., limit=...)` |
| 설비 점검 필요, 재학습 보류 | 설비 담당자, 서비스 운영자 | `[WARN] facility check required - retrain held (outage_days=..., hold_days=...)` |
| 하루 점검 알림 | 설비 담당자 | `[WARN] daily output low - facility check suggested (date=..., ratio=...)` |

| 입력 이상 의심 | 서비스 운영자 | `[WARN] input anomaly suspected - rmse21=... > limit ...` |

- **[현재]** 위의 세 문장만 코드에 있다(`retrain_trigger.py` 43, 55, 85 ~ 87행). 아래 여섯은 **[제안]** 이고 코드에 없다.
- **[현재]** 알림 수단은 `logs/aiops.log` 파일과 그것을 보여 주는 대시보드의 로그 패널이다. 대시보드는 로그를 스스로 새로 읽지 않는다. 사람이 단추를 눌러야 내용이 보인다. **메일이나 메신저로 보내는 알림은 없다.**
- **[현재]** 재학습이 게이트에서 막히면 `aiops.log` 에 경고와 재학습 시작의 두 줄은 남지만 결과의 줄이 남지 않는다. 결과는 승격했을 때만 쓴다(`retrain_trigger.py` 84 ~ 89행). 서버의 표준 출력에는 `[GATE FAILED]` 가 찍히고 응답에는 `promoted: false` 가 실린다. **[과제]** 실패의 문장을 로그에 더한다.
- **[제안]** 발표 범위에서는 로그 파일이 알림 창구다. 밖으로 보내는 알림은 만들지 않고 후속 과제로 둔다.
- **[실행]** 지금의 `aiops.log` 는 비어 있다(0바이트). 경고가 남는 경로가 한 번도 돌지 않았다. ([V09](evidence/validation.md#v09), [V13](evidence/validation.md#v13))

### 9. 재학습

**[제안]** [0008](../decisions/0008-retraining-and-version-switch.md)을 따른다.

| 항목 | 값 | 성격 |
| --- | --- | --- |
| 자료 | 가장 최근에 올린 파일의 마지막 41행(입력 20일 + 판정 21일) | **[현재]** `retrain_trigger.py` 65행. 행 수를 정하는 자리가 빈칸이다 |
| 거는 때 | 배치 41행의 앞 20일과 뒤 21일의 성능 지표가 **함께** 임계값 아래일 때. 뒤 21일만 아래이면 알리기만 하고 기다린다 | **[제안]** 지금은 드리프트로 판정되면 곧바로 건다 |
| 나누기 | 표본 21개. 앞 16개로 학습, 뒤 5개로 게이트 | **[현재]** `train_and_register.py` 의 `_prepare`. 21 × 0.8 = 16.8 을 내려 16 |
| 학습 방식 | 이어서 학습(warm start). 지금의 Production 가중치에서 시작한다. 학습률 1e-4, 10 epoch | **[현재]** `fine_tune`, `FINE_TUNE_LR`, `FINE_TUNE_EPOCHS` |
| 스케일러 | 다시 맞추지 않는다 | **[현재]** |
| 겹쳐 도는 것을 막기 | 재학습 중에는 새 재학습을 시작하지 않는다. 같은 끝 날짜의 자료로는 다시 재학습하지 않는다. 재학습을 마치면 쌓아 둔 최근 예측 기록을 비운다 | **[제안]** 지금은 막는 장치가 없다 |
| 정지와 보류 | 41행 안에 있으면 재학습하지 않는다 | **[제안]** |

- 경고가 처음 켜진 날에 곧바로 재학습하지 않는 까닭: 그날의 41행에는 내려가기 전의 날이 섞여 있다. **[조사]** 조사가 재학습의 효과를 잰 조건은 "내려간 뒤의 행만으로 된 41행"이다([T5](../research/merged/T5-drift-demo.md)). 섞인 자료로 재학습했을 때의 결과는 아무도 재지 않았다. 그래서 앞 20일도 내려간 수준이 된 뒤에 건다.
- **[실행]** 이 조건이 언제 채워지는지 2025년의 자료로 세어 보았다. 변화가 없으면 37개 시작일 가운데 한 번도 채워지지 않았다. 14% 를 낮추면 32개에서 채워졌고 가운데 값이 26일째(7 ~ 35일째)였다. 8.5% 를 낮추면 28개에서 채워졌고 가운데 값이 31일째(9 ~ 39일째)였다. 열흘 안팎으로 이르게 채워진 것은 변화가 없어도 임계값을 넘던 4월의 구간 바로 뒤에 시작한 경우다. 시연 배치(2025-06-21 ~ 07-31)는 그대로면 앞 20일 −2.8%, 뒤 21일 −2.2% 이고, 0.86 을 곱하면 −16.3%, −15.6% 라 조건을 채운다. ([V22](evidence/validation.md#v22))
- 그 사이에는 알림만 나가고 예측은 이전 모델이 한다. 모델이 스스로 낮아진 수준을 얼마나 따라가는지는 우리 모델로 재지 않았다.
- 처음부터가 아니라 이어서 학습하는 까닭: 41행으로는 처음부터 학습할 수 없다. 표본이 21개뿐이다.
- 학습률과 epoch 를 키우지 않는 까닭: **[조사]** 1e-3, 50 epoch 로 키우면 변화가 없는 구간에서 RMSE 가 40.3kWh 에서 48.8kWh 로 올랐다. 실습 설정에서는 40.3kWh 대 40.7kWh 로 그대로였다. 학습이 2025-02-28 에서 끝나는 다른 모델의 저장된 결과다([T5](../research/merged/T5-drift-demo.md)).
- **[현재]** 재학습은 `POST /predict/batch-test` 의 응답 안에서 돈다. 끝날 때까지 그 요청이 응답하지 않는다.
- **[현재]** 재학습 자료는 받은 배치가 아니라 "가장 최근에 올린 파일"의 끝이다. 시연하는 배치의 날짜와 파일의 끝 날짜가 다르면 엉뚱한 구간으로 재학습한다. 오류는 나지 않는다. **[제안]** 발표에서는 배치의 끝 날짜에서 자른 사본을 올려 맞춘다. **[실행]** 2025-07-31 에서 자른 파일의 마지막 41행이 시연 배치(2025-06-21 ~ 07-31)와 같은 날짜임을 확인했다. ([V21](evidence/validation.md#v21))

41행 재학습의 한계는 다음과 같다.

- 표본이 21개다. 수준이 바뀐 뒤의 자료만으로 계절이나 날씨의 폭을 다시 배울 수 없다. 할 수 있는 일은 수준을 조금 옮기는 것이다.
- 창이 겹친다. 이웃한 표본은 입력 20일 가운데 19일이 같다.
- 수준이 바뀐 날이 41행의 중간에 있으면 바뀌기 전과 뒤의 자료가 섞인다. 위의 "거는 때"가 이것을 줄이려는 조건이지만, 앞 20일의 편차가 임계값을 넘는 순간에도 앞쪽 며칠은 바뀌기 전의 날일 수 있다.

### 10. 게이트로 다시 확인하고, 실패하면 유지하고, 필요하면 되돌린다

세 가지는 서로 다른 일이다.

| 일 | 뜻 | 지금 | 제안 |
| --- | --- | --- | --- |
| 게이트 재검증 | 재학습한 모델을 올리기 전에 다시 확인한다 | 뒤 5건의 RMSE 가 4.00 이하 | 뒤 5건의 RMSE 가 처음 학습 때 저장한 합격선(지금 자료면 47.5kWh) 이하 |
| 기존 버전 유지 | 게이트에서 막힌 모델을 올리지 않는다. 운영 버전에는 아무 일도 일어나지 않는다 | 있다 | 그대로. 로그에 남긴다 |
| 되돌리기(롤백) | **이미 올린** 버전을 내리고 이전 버전으로 돌아간다 | 없다 | 손으로 하는 절차로 둔다 |

재학습 게이트는 **기능 시연용**이다. 품질을 보증하지 못한다.

- **[조사]** 변화가 없는 구간에서 재학습한 뒤의 5건 RMSE 는 가운데 36.7kWh, 5% 16.6kWh, 95% 76.0kWh 로 크게 흔들린다. 합격선이 45kWh 이면 통과율이 주입 없음 65.9%, 14% 하락 주입 75.2% 다. 5건의 RMSE 와 그 뒤 21일 RMSE 의 상관은 0.36 이다. 학습이 2025-02-28 에서 끝나는 다른 모델의 저장된 결과이고, 우리 모델과 47.5kWh 의 합격선으로는 재지 않았다. ([T5](../research/merged/T5-drift-demo.md))
- 그래서 통과와 실패가 모두 정상 동작이다. 통과를 보이려고 실행한 뒤에 기준을 바꾸지 않는다.
- **[제안]** 재학습으로 올라간 버전은 바뀐 뒤의 자료가 180일 쌓이면 처음 학습과 같은 상대 기준으로 다시 평가한다. 발표 범위에서는 설계다.

되돌리기는 레지스트리 수준에서 확인했다.

- **[실행]** 앱의 승격과 같은 두 호출을 하면 버전 1 과 2 가 함께 Production 이 되고, `models:/HAIC_Predictor/Production` 은 버전 2 를 가리킨다. 버전 2 를 Archived 로 내리면 다시 버전 1 을 가리킨다. 앱의 재학습을 돌린 결과가 아니라 MLflow 의 동작을 따로 확인한 것이다. ([V16](evidence/validation.md#v16))
- **[제안]** 손 절차: 새 버전을 Archived 로 내린다 → 서빙 모델을 다시 불러온다 → `/health` 의 버전을 확인한다.
- **[과제]** 승격할 때 이전 버전을 Archived 로 내린다. 지금은 두 버전이 함께 Production 에 남는다.

### 11. 승격한 뒤 서빙 모델을 바꾼다

MLflow 에서 승격한 것과, 떠 있는 서버가 새 모델로 답하는 것은 별개의 일이다.

| 항목 | 지금 | 제안 |
| --- | --- | --- |
| 메모리의 모델 | 한 번 불러오면 계속 쓴다. 승격 뒤에 바꾸는 코드가 없다 | 승격에 성공하면 새 모델을 먼저 불러오고, 불러오는 데 성공했을 때만 바꾼다. 실패하면 이전 모델로 계속 답하고 로그에 남긴다 |
| 모델을 읽는 곳 | `MODEL_SOURCE` 의 기본값이 `local` 이다. 서버를 다시 띄워도 MLflow 의 새 버전을 읽지 않는다 | 운영은 `MODEL_SOURCE=mlflow` 로 띄운다. 컨테이너는 이미 그렇게 돼 있다 |
| 응답의 `model_version` | `"v1-local"` 이나 `"production"` 이라는 고정된 글자 | 레지스트리의 버전 번호(예: `"v2"`) |
| `/health` | 모델이 올라왔는지만 알린다 | 올라와 있는 버전도 알린다 |
| 바뀌었는지 확인 | 방법이 없다 | **레지스트리의 Production 버전과 서버가 불러온 버전이 같은지**를 본다. 응답의 글자만으로 판단하지 않는다 |

- **[현재]** 메모리의 모델을 바꾸는 줄은 `model_loader.py` 안에만 있고 재학습과 승격 경로에는 없다. 코드를 읽어 센 값이다. 서버에서 실행해 확인한 것은 아니다. 빈칸 때문에 재학습 경로가 돌지 않는다. ([V02](evidence/validation.md#v02))
- **[실행]** `MODEL_SOURCE=mlflow` 로 띄우면 eager 에서는 스케일러를 불러오는 자리의 빈칸(125행)에서 서버가 뜨지 못하고(종료 코드 3), lazy 에서는 서버는 뜨지만 `/predict` 가 167행의 빈칸에서 500 이다. ([V14](evidence/validation.md#v14))

| 30%, 70%, 50%, 30kWh, 80kWh, 7일 가운데 3일 | 정지, 낮은 날, 하루 알림, 보류 | [0007](../decisions/0007-facility-vs-model-branch-and-alerts.md) | 없다 |

### 13. 구현 과제와 확인하지 못한 것

**[과제]** 이 설계를 코드로 옮기려면 다음이 필요하다. 순서대로다.

1. 빈칸 11곳을 HAIC 실습의 답으로 채워 원래의 흐름이 끝까지 도는지 확인한다.
2. 요청 스키마를 고친다(`close` 0 이상과 상한, `volume` 소수와 상한, 날짜).
3. 업로드 검증을 더한다(숫자, 빈 값, 날짜의 순서와 연속성, 범위).
4. 게이트를 상대 기준으로 바꾸고 치우침을 본다. 합격선과 기준선을 저장한다.
5. 배치 요청이 예보, 날짜, 기대 발전량을 받게 하고 성능 지표로 판정한다. 최근 41일을 날마다 보내는 일을 자동으로 돌린다.
6. 정지와 보류의 갈래를 넣고 로그 문장을 더한다.
7. 승격 뒤 서빙 모델을 다시 불러오고 실제 버전 번호를 응답에 싣는다.
8. 앞 20일까지 내려갔을 때만 재학습하게 하고, 겹쳐 돌지 않게 한다.

코드의 어느 줄을 고치는지는 [④ 의 6절](4-architecture.md#6-haic-스켈레톤에서-바꿀-곳과-그대로-둘-곳)에 있다.

| 확인하지 못한 것 | 이 문서에서 어떻게 다뤘는가 |
| --- | --- |
| 감시, 분기, 재학습, 승격 뒤 교체가 서버에서 실제로 도는지 | 설계라고 적었다. 코드를 읽어 적은 것은 "지금"으로, 돌려 본 것은 "실행"으로 갈랐다 |
| 임계값과 한도가 다른 해에서도 맞는지 | 표본 안의 값이라고 적었다 |
| 관측 날씨를 날마다 받을 수 있는지. 2026-01 ~ 02 는 받지 못했다 | 감시는 2025-12-31 까지의 자료로만 계산했다 |
| 재학습 게이트가 시연 날짜에서 통과하는지 | 통과와 실패를 모두 정상으로 두었다 |
| 승격 뒤 두 버전이 함께 Production 일 때 서버가 무엇을 읽는지 | 레지스트리 수준에서만 확인했다. 서버에서의 확인은 과제다 |

후속 조건은 [`../followups.md`](../followups.md)에 옮겨 적었다.

### 14. 여러 발전소일 때의 게이트, 감시, 재학습 (확장 제안)

**[현재]** 1 ~ 13절은 발전소 한 곳의 정책이다. 이 절은 발전소가 여럿일 때 **대상별로** 무엇이 달라지는지를 적는다. 모두 **[제안]** 이고 구현하지 않았다. 근거는 [0010](../decisions/0010-multi-plant-scope-and-scheme.md), [0011](../decisions/0011-multi-plant-forecast-and-identity.md), [0012](../decisions/0012-single-pc-retrain-jobs.md)이고 담당별 계약은 [확장 문서 8절](multi-plant-extension.md#8-담당별-변경-계약)에 있다.

원칙은 하나다. **1절의 정책을 발전소마다 따로 돌리고, 합계는 따로 본다.** 한 발전소에서 생긴 일이 다른 발전소의 게이트, 판정, 재학습에 들어가지 않는다.

| 단계 | 대상 | 여러 발전소일 때 더하는 것 | 근거 |
| --- | --- | --- | --- |
| 요청 검증 | 발전소 | `plant_id` 가 등록부에 있는지 본다. 발전량의 상한을 1,320kWh 고정값이 아니라 그 발전소의 설비 용량 × 24시간으로 본다 | [0011](../decisions/0011-multi-plant-forecast-and-identity.md) |
| 업로드 검증 | 발전소 | 대상 발전소와 자료 종류를 받아 발전소별 폴더에 둔다. 다른 발전소의 행이 섞인 파일을 막는다 | [자료 계약 3절](multi-plant-data-contract.md#3-검증-정책) |
| 자료의 품질 | 발전소 | 결측을 0 으로 채우지 않는다. 결측이 낀 창은 만들지 않는다. 창은 발전소별로, 날짜가 이어진 구간에서만 만든다 | [자료 계약 1절](multi-plant-data-contract.md#b-발전-실적) |
| 배포 게이트 | 발전소 | 4절의 기준을 발전소마다 그 발전소의 기준 예측으로 본다. 시험 구간은 포트폴리오의 모든 발전소가 같은 날짜다. 실패하면 **그 발전소의** 이전 버전만 유지한다 | [0005](../decisions/0005-deployment-gate.md), [0011](../decisions/0011-multi-plant-forecast-and-identity.md) |
| 합계의 품질 | 포트폴리오 | 공통 시험일에서 합계의 RMSE 가 합계에 대한 7일 평균의 80% 이하, 치우침 ±10% 이내인지를 계산해 기록한다. **승격을 막지 않는다.** 포트폴리오 응답의 "검증됨" 표시에만 쓴다 | [0011](../decisions/0011-multi-plant-forecast-and-identity.md) |
| 모델과 스케일러의 짝 | 발전소 | 불러올 때 묶음 기록의 발전소와 스케일러의 해시를 견준다. 어긋나면 불러오지 않고 그 발전소만 503 이다 | [0011](../decisions/0011-multi-plant-forecast-and-identity.md) |
| 감시 | 발전소 | 5절의 판정을 발전소마다 한다. 창, 기준선, 마지막 판정일, 경보 상태를 발전소별로 둔다 | [0006](../decisions/0006-monitoring-metric-and-thresholds.md) |
| 감시 | 포트폴리오 | 같은 날짜의 합계에서 성능 지표와 오차를 따로 본다. 합계의 기준선은 구성 버전마다 다시 계산한다. 구성이 바뀐 날을 걸친 합계의 판정은 하지 않는다 | [확장 문서 8.3절](multi-plant-extension.md#83-aiops) |
| 분기 | 발전소와 포트폴리오 | 아래 그림. 자료가 들어오지 않은 발전소는 저하로 세지 않는다. 용량의 절반 넘는 구성원이 함께 내려가면 공통 요인을 의심하고 개별 재학습을 미룬다 | [0007](../decisions/0007-facility-vs-model-branch-and-alerts.md) |
| 알림 | 발전소와 포트폴리오 | 8절의 문장에 `plant=`, `model=`, `data=`, `job=` 을 싣는다. 합계의 문장에는 `portfolio=` 와 구성 버전을 싣는다 | [확장 문서 8.3절](multi-plant-extension.md#83-aiops) |
| 재학습 | 발전소 | 9절의 조건을 채운 발전소만 건다. 요청 안에서 돌리지 않고 작업으로 적는다. 한 번에 하나만 돌고, 같은 발전소의 같은 끝 날짜로는 다시 돌지 않는다 | [0012](../decisions/0012-single-pc-retrain-jobs.md) |
| 승격 뒤 서빙 | 발전소 | 메모리의 모델 상자를 발전소별로 둔다. 재학습 일꾼이 승격하면 그 발전소의 현재 버전 표시를 바꾸고, 서빙은 표시가 다르면 새 모델을 먼저 불러온 뒤 바꾼다 | [0012](../decisions/0012-single-pc-retrain-jobs.md) |
| 되돌리기 | 발전소 | 10절의 손 절차를 발전소 하나에 대해 한다. 버전 번호는 발전소마다 따로 간다 | [0008](../decisions/0008-retraining-and-version-switch.md) |

발전소별 판정과 합계의 판정이 갈라지는 순서다.

```mermaid
flowchart TD
    start["하루의 판정<br/>발전소마다 최근 41일"] --> data{"그 발전소의 자료가<br/>들어왔는가"}
    data -- "아니오" --> missing["data_missing<br/>저하로 세지 않는다<br/>합계에서 '빠진 발전소'"]
    data -- "예" --> single["발전소별 판정<br/>7절의 갈래 그대로<br/>정지·보류 / 수준 저하 / 입력 이상 / 정상"]
    single --> collect["같은 날의 판정을 모은다"]
    collect --> change{"구성 버전이<br/>창 안에서 바뀌었는가"}
    change -- "예" --> skip["합계의 판정을 하지 않는다<br/>구성 변경은 드리프트가 아니다"]
    change -- "아니오" --> common{"저하로 판정된 구성원이<br/>설비 용량의 절반을 넘는가"}
    common -- "예" --> shared["공통 요인 의심<br/>날씨나 예보 입력을 본다<br/>개별 재학습을 미룬다"]
    common -- "아니오" --> each["발전소별 대응<br/>정지·보류는 점검 알림<br/>수준 저하는 재학습 후보"]
    each --> job["조건을 채운 발전소만<br/>재학습 작업으로 적는다<br/>한 번에 하나"]
    job --> gate{"그 발전소의<br/>게이트 통과"}
    gate -- "예" --> promote["그 발전소만 승격<br/>현재 버전 표시를 바꾼다"]
    gate -- "아니오" --> keep["그 발전소의 이전 버전 유지<br/>다른 발전소는 영향 없음"]
```

**이 절의 숫자가 사는 곳.** 12절의 표에 더하는 것이다.

| 숫자 | 뜻 | 근거 | 지금 코드의 값과 위치 |
| --- | --- | --- | --- |
| 설비 용량 × 24시간 | 발전소별 발전량의 입력 상한 | [0011](../decisions/0011-multi-plant-forecast-and-identity.md) | `MAX_GENERATION_KWH = 1320.0`, `serving_app/schemas.py:9`. 55kW 기준의 고정값이다. 바꾼다 |
| 80%, ±10% | 합계의 "검증됨" 기준(합계에 대한 7일 평균 대비, 치우침) | [0011](../decisions/0011-multi-plant-forecast-and-identity.md) | 없다 |
| 설비 용량의 절반 | 함께 내려갔을 때 공통 요인으로 보는 한도 | [확장 문서 8.3절](multi-plant-extension.md#83-aiops) | 없다. **[미확인]** 재 본 적이 없는 출발값이다 |
| 0.55kWh/kW, 1.45kWh/kW | 정지와 낮은 날을 가르는 기대 발전량의 하한(7절의 30kWh, 80kWh 를 55kW 로 나눈 값) | [0007](../decisions/0007-facility-vs-model-branch-and-alerts.md) | 없다. **[미확인]** 다른 발전소에서 맞는지 재지 않았다 |
| 1 | 동시에 도는 재학습의 수 | [0012](../decisions/0012-single-pc-retrain-jobs.md) | 없다. 지금은 요청 안에서 돈다 |

| 5MB·20,000행, 400행, 200곳 | 업로드, 배치 요청, 포트폴리오 요청의 한도 | [0012](../decisions/0012-single-pc-retrain-jobs.md) | 없다. 지금은 한도가 없다 |

**[실행]** 지금의 코드가 발전소 한 곳을 전제로 한다는 것은 읽은 결론에 그치지 않고 재현했다. 마지막에 올린 파일이 다른 발전소의 학습에 쓰이는 것, 발전소의 행을 이어 붙이면 섞인 창이 오류 없이 생기는 것, 다른 발전소의 스케일러가 붙어도 오류가 나지 않는 것, 큰 발전소의 정상 값이 1,320kWh 에 걸리는 것이다. ([M07](evidence/multi-plant/validation.md#m07))

**[과제]** 구현의 순서와 끝났다고 보는 기준은 [확장 문서 9절](multi-plant-extension.md#9-다음-구현-작업)에 있다. 13절의 과제가 먼저다. 발전소 한 곳의 게이트와 판정이 서버에서 돌아야 그것을 발전소마다 돌릴 수 있다.

| 확인하지 못한 것 | 이 문서에서 어떻게 다뤘는가 |
| --- | --- |
| 여러 발전소의 게이트, 판정, 재학습이 서버에서 도는지 | 설계라고 적었다. 서비스는 발전소 한 곳만 다룬다 |
| 임계값과 한도(−7.5%, 15일, 용량에 비례하게 바꾼 하한)가 다른 발전소에서도 맞는지 | 하수처리장에서 고른 값이라고 적었다 |
| 공통 요인으로 보는 한도(설비 용량의 절반)가 맞는지 | 출발값이라고 적었다. 같은 군의 발전소는 날씨를 함께 겪어 함께 움직인다 |
| 합계의 "검증됨" 기준이 모델에서 통과하는지 | 기준 예측의 값만 있다([② 의 11절](2-solution-and-goals.md#11-여러-발전소로-넓힐-때의-예측과-목표-확장-제안)) |
